## 0. 固定约束确认

| 约束 | 决策 |
|---|---|
| 语言/框架 | Java 21 LTS + Spring Boot 3.5.16 |
| AI 框架 | Spring AI 1.1.2 双协议核心库（`spring-ai-openai` + `spring-ai-anthropic`）为业务抽象，OpenAI 兼容 + Anthropic Messages 两类协议按配置切换 |
| 数据库 | SQLite 3（`sqlite-jdbc` 3.50.3.0，嵌入式单文件库），唯一持久化存储；WAL 模式；本地缓存用 Caffeine，**不引入 Redis** |
| 前端 | Vue 3 + Vite，前后端分离；Nginx 托管静态资源并反代 `/api` |
| 部署 | 单台服务器（应用 + Nginx 同机；SQLite 为进程内嵌入式库，无独立数据库服务），部署流程越简单越好 |
| 其他隐含约束 | 单人开发维护；无 MQ、无微服务、无多实例；盘后批处理为主、API 查询为辅 |

## 1. 技术选型清单（含理由）

| 项 | 选型 | 理由 / 备选 |
|---|---|---|
| JDK | Java 21 LTS | Boot 3.5 要求 17+；**虚拟线程**用于流水线内每只标的的并行 LLM 调用，收益直接 |
| Web 框架 | Spring Boot 3.5.16（webmvc，非 WebFlux） | 盘后批处理 + 少量 API，阻塞式模型足够，调试简单 |
| AI 框架 | Spring AI 1.1.2 + `spring-ai-openai` + `spring-ai-anthropic` | 业务代码只面向 `ChatClient`；一份配置支持 OpenAI 协议（火山方舟 Coding Plan / DeepSeek / DashScope 兼容模式 / 任意自建 OpenAI 兼容服务）与 Anthropic Messages 协议（Claude 官方 / one-api、new-api、LiteLLM 等自建服务）；多 profile 手动构建 ChatModel，不使用 starter auto-config（T7） |
| ORM | **MyBatis-Plus 3.5.15（已落地，2026-11-24 ORM 化）** | 业务表用实体 + `BaseMapper` + `LambdaQueryWrapper`；41 张 Tushare 表批量 upsert（SQLite `INSERT ... ON CONFLICT ... DO UPDATE`）由 MyBatis 动态 SQL Provider 承载；批量写走 MyBatis BATCH 执行器（500 行/批）；DDL 用 MyBatis `ScriptRunner`。**生产代码不使用 `JdbcTemplate`**（仅测试夹具/断言），见 §10 ADR-2 / ADR-12。备选：JPA（upsert 别扭，不推荐） |
| 数据库 | SQLite 3（`org.xerial:sqlite-jdbc` 3.50.3.0，runtime） | 单机个人系统：嵌入式单文件库，零安装/零运维、单文件备份、测试与生产同引擎可真实全量验证；备选：MySQL 8（需独立服务进程，2026-11-24 迁移后弃用）、H2（仅测试内存库，已删除） |
| 数据库初始化 | 启动期执行 `db/schema.sql`（`SqliteSchemaInitializer`，`@PostConstruct`） | SQLite 无独立建库步骤；schema 全部 `IF NOT EXISTS`，启动自动建齐 58 表（幂等）；开发期删库文件重建，不做迁移（ADR-7） |
| JSON 处理 | fastjson2 2.0.61 | JSON TypeHandler、FactBundle/判断块序列化、LLM 响应解析容错；全项目统一 JSON 库，不混用 Jackson 做业务序列化（Spring 内部 Jackson 不受影响）。**当前例外**：`quality_check_log.items` 由 `QualityCheckLogStore` 用 Jackson 序列化（历史实现，见 §5.2；T6+ 业务表统一走 fastjson2 / JSON TypeHandler） |
| 通用工具 | Hutool 5.8.44 + commons-lang3 3.20.0 | 日期/字符串/Bean 工具，减少自造轮子 |
| 技术指标计算 | ta4j 0.22.6 | L1 compute 单元的指标库：均线、RS、波动率、支撑压力等（`calc_trend_strength` 等），避免手写指标 |
| 统计计算 | commons-math3 3.6.1 | 分位数/经验 CDF（估值分位）、描述统计（`calc_valuation_percentile` 等） |
| API 文档 | springdoc-openapi 2.8.6 | Web 接口自文档化（个人项目也值得，前端联调方便） |
| 本地缓存 | Caffeine 3.x + Spring Cache 抽象 | 参考数据缓存（股票列表/交易日历/行业映射/受控词表/当前方法版本）；具名缓存 TTL/容量集中登记在 `CacheSpec`，方法级临时缓存用 `@LocalCache`。**不引入 Redis** |
| 调度 | Spring `@Scheduled` + 触发表轮询 | 单实例无需分布式锁/Quartz；事件触发与手动重跑走触发表，由每分钟轮询消费 |
| 限流 | Guava 33.6.0-jre（`RateLimiter`）+ 自研滑动窗口计数（单机内存） | `RateLimiter` 做 Tushare 出流平滑（按 api_name 包装），滑动窗口计数主控、计数旁路落表；阈值取手册附录 B 留 10~25% 余量 |
| JSON Schema 校验 | networknt json-schema-validator 2.0.0 | L3 判断块硬校验（能力详案第 3 章，实现在 `capability.runtime.validation.SchemaValidator`；仅此处用 Jackson 读 Schema 资源，业务 JSON 仍统一 fastjson2） |
| HTTP 客户端 | Spring RestClient | 调 Tushare HTTP 接口（手册第 2 章契约） |
| 日志 | Logback 滚动文件 | 无外部日志服务；MDC traceId 贯穿请求与批处理，级别约定见《公共基础设施使用手册》第 3 节 |
| 参数校验 | spring-boot-starter-validation（Hibernate Validator） | `@Valid` + 自定义 `@EnumCode`（取值必须是字典枚举的合法 code），失败统一 400 |
| 切面/AOP | spring-boot-starter-aop（AspectJ weaver） | `@LocalCache` / `@LocalCacheEvict` 方法级缓存注解的实现基础 |
| 分页 | mybatis-plus-jsqlparser（`${mybatis-plus.version}`） | MyBatis-Plus 3.5.9+ 分页插件独立模块；`PaginationInnerInterceptor` 必须注册，否则 `IPage` 不生成 LIMIT |
| 样板代码 | Lombok（optional） | 编译期消除样板代码，不出现在运行时 |
| 构建部署 | Maven 单体 + systemd + scp | 见第 8 章；不引入 Docker 作为首选（可选替代方案） |

**明确不引入**（按需再看）：Redis、MQ（模块间用 Spring `ApplicationEvent`）、Quartz、Elasticsearch、对象存储（报告文件直接落磁盘）。

### 2.2 部署视图（单服务器）

```
服务器（建议 2C4G 起步，4C8G 更从容）
├── Nginx          :80/443   → 静态资源 /var/www/refine-loop + /api 反代 127.0.0.1:8080
├── refine-loop.jar（systemd 服务）:8080   JVM -Xmx1g -Xss512k（虚拟线程）
└── /data/refine-loop/
    ├── db/                 SQLite 单文件库 refine_loop.db（WAL 模式，另有 -wal / -shm 伴随文件）
    ├── reports/            盘后报告 markdown 按日归档
    ├── backup/             库文件每日 02:00 备份（VACUUM INTO 或 sqlite3 .backup），保留 14 天
    └── logs/               应用日志滚动
```

> 相比 MySQL：无独立数据库进程与端口监听，备份对象是库文件（含 WAL 时先做 checkpoint 或用 `VACUUM INTO` 生成一致性快照），删库文件即整库重建。

## 3. 应用模块划分与包结构

**决策：单 Maven 模块，按领域分包**（单人开发优先控制构建/部署复杂度；未来确需拆分再转多模块，包边界已按可拆分设计）。

```
com.arthur.refineloop          （注：早期设计稿写 com.refine.loop，T1 落地时以现有代码为准）
├── common/                  通用层（公共基础设施；使用手册见《公共基础设施使用手册》）
│   ├── (root)               Result / PageResult / ApiException：统一响应与业务异常
│   ├── error/               ErrorCode 契约 + CommonErrorCode 通用码（0 成功 / 4xx·5xx 沟通层 / 1xxx 业务）
│   ├── constant/            HeaderNames / DatePatterns / CacheNames / CommonConstants
│   ├── page/                PageQuery（校验 + offset/limit）、PageResults（MyBatis-Plus 适配）
│   ├── dict/                DictEnum / DictItem / DictProvider / DictService / DictController / DictTypes
│   ├── enums/               内置字典枚举（YesNo / EnableStatus / SortOrder）
│   ├── cache/               CacheSpec / CacheConfig / CacheTemplate / @LocalCache / @LocalCacheEvict
│   ├── log/                 TraceContext / TraceIdFilter / RequestLogFilter / MdcTaskDecorator
│   ├── util/                Strings / Asserts / JsonUtils / DateTimes / Decimals / Numbers / Enums
│   │                        Ids / MaskUtils / RetryUtils / ThreadPools / StopWatch / Csvs / Trees
│   └── validation/          @EnumCode + 校验器（枚举取值校验）
├── config/                  Spring配置：MyBatis-Plus/Sqlite 初始化、AI、缓存（CacheConfig）、
│                            异步线程池（AsyncConfig）、OpenAPI、线程池参数（ThreadPoolProperties）
├── data/                    数据访问层（2026-11-24 ORM 化；全系统唯一 SQL 出入口）
│   ├── entity/              MyBatis-Plus 实体：ingest_log / sys_config / rate_limit_counter / quality_check_log
│   │                        （@TableName + @TableId(IdType.AUTO)，字段与 schema 一一对应，JSON 语义列用 String）
│   ├── mapper/              8 个 @Mapper：业务表 BaseMapper + 注解 SQL；41 张镜像表动态 SQL；固定业务查询；
│   │                        质量门聚合与今日运维统计

│   └── handler/             SqliteLocalDateTimeTypeHandler：LocalDateTime ↔ SQLite 文本时间戳（与 date_class=TEXT 同口径）
├── ops/                     运维读模型域（2026-11-24 新增；只读聚合，web 不再直连 mapper）
│   ├── TableOpsService      41 表总览/详情/预览/行数统计/每日开关切换
│   ├── StatsService         今日运维统计（作业/调用量/健康度/质量门/编排）
│   ├── QualityOpsService    质量检查历史（天数/分页校验 + 视图映射）
│   ├── IngestOpsService     作业历史分页、单表动作、状态归一与表名白名单
│   ├── OpsParams            运维参数校验（表名白名单/预览深度/日期格式）
│   ├── OpsViews             运维 API 响应视图（record 集合）
│   └── PreviewSpec          数据预览过滤参数（替代长参数列表）
├── tushare/                 数据接入模块
│   ├── client/              TushareClient（RestClient + 契约封装）
│   ├── ratelimit/           RateLimiterRegistry（按api_name滑动窗口）+ 计数旁路（MyBatis）
│   ├── ingest/

**数据访问层强制约定（`data` 包，2026-11-24 ORM 化）：**

1. **禁止在 service 里直接写 SQL 字符串，禁止生产代码使用 `JdbcTemplate`**（`JdbcTemplate` 只允许出现在测试夹具/断言）：业务表走 MyBatis-Plus 实体 + `BaseMapper` / `LambdaQueryWrapper`，固定查询走类型化 `@Mapper` 注解 SQL；
2. **41 张 Tushare 镜像表不逐表写 Mapper/XML**：注册表 `fields` 是唯一列事实源，由 `TushareSqlProvider` 按「表名 + 列串 + 幂等键」动态生成 INSERT / `ON CONFLICT` / DELETE / COUNT / MAX / GROUP BY / 预览 SQL，避免 41 份手写 SQL 与注册表漂移（原 D2 决策的延续，执行层由 `JdbcTemplate` 换成 MyBatis）；
3. **批量写统一走 `MyBatisBatchExecutor`**：500 行/批 flush，`replaceAll` / `deleteAndInsertBlock` 用同一 BATCH 会话 + 一个事务保证「先删后插」原子；同一事务内不得混用不同 `ExecutorType` 的会话（MyBatis-Spring 限制，已在实现中规避）；
4. **DDL / PRAGMA 也走 MyBatis**：schema 由 `SqliteSchemaInitializer` 用 MyBatis `ScriptRunner` 执行 `db/schema.sql`；`PRAGMA table_info` 列元数据由 Provider Mapper 执行——因此生产代码零 `JdbcTemplate`；
5. `mapper-locations: classpath*:/mapper/**/*.xml` 为未来 XML 预留，当前无 XML（自定义 SQL 均为注解/Provider）。

## 4. 核心模块详细设计

### 4.1 数据接入模块 `tushare`

职责：把《Tushare 接口对接手册》40 接口/41 表的契约代码化，是全系统唯一的数据入口。

| 组件 | 设计要点 |
|---|---|
| `TushareClient` | 封装 POST `api.tushare.pro`：token 从环境变量注入；列式响应按下标对齐转 `List<Map>` / POJO；错误码 `40203/50101` 分型处理 |
| `RateLimiterRegistry` | 按 `api_name` 独立滑动窗口计数（**主控**，对齐自然分钟），Guava RateLimiter 仅做平滑出流；阈值取手册附录 B 留 10~25% 余量（如 `share_float` 60→48 次/分钟）；超限**阻塞等待**到下一窗口而非失败重试；计数旁路写 `rate_limit_counter` 供观测 |
| `IngestOrchestrator` | **每日 ingest 编排（S0 的前置依赖）**：按依赖分层调度——维表层（stock_basic/trade_cal/行业映射）→ 行情层（daily/adj_factor/daily_basic）→ 财务与事件层（fina 类/公告类）；每表作业记录起止时间/行数/状态到 `ingest_log`；作业失败退避重试 3 次，仍失败置 FAILED 并**即时告警**（不等 S0 兜底）。M1 停用 `hk_hold` 每日拉取作业（2024-08 起断供，表结构保留，M2 评估后再启） |
| `IngestJobService` | 实现手册第 4 章五种更新策略（全量/按日增量/按股增量/按期循环/整公告重写）；幂等写入**三分法**（对齐手册 3.3）：行业务主键类 upsert（`TushareTableMapper` 动态 SQL Provider + SQLite `INSERT ... ON CONFLICT (键) DO UPDATE SET 列 = excluded.列`）、公告/报告期整块类**按业务键先删后插**（防更正重发新旧并存，同一 BATCH 会话 + 一个事务原子提交）、维表类全量替换；幂等键按手册附录 C，批量 500 行/批经 `MyBatisBatchExecutor`（MyBatis BATCH 执行器）flush，HTTP 调用不包事务；落库经 `IngestTableWriter` 统一出入口（见下方单写者约定） |
| `DataQualityGate` | 流水线 S0 数据门，**双层判定**：① 查当日 `ingest_log` 关键表作业状态（FAILED/未完成即不达标）；② 行数与一致性校验（当日 `daily` 行数 vs `stock_basic` 在市总数偏差、`adj_factor` 与 `daily` 同日行数一致、关键字段 sanity 抽样如 close≤0 行数告警）、关键表时效校验；不达标挂起整线告警（总纲 5.5） |

注意：`fina_mainbz`（单次100行按期循环）、`report_rc`（1次/分钟）按手册第 3 章特殊规则单独实现。

**SQLite 单写者约定**：Tushare 表落库由 `IngestTableWriter` 统一出入口，进程内用 `ReentrantLock` 串行化写操作（HTTP 并发拉数不变，只把落库串行化；批量语句跑在 `MyBatisBatchExecutor` 的 BATCH 会话里），配合数据源 `busy_timeout=5000` 与 WAL 模式避免 `SQLITE_BUSY`；运维 API 的行数统计经 `TushareTableMapper.countAll` 精确 `COUNT(*)`（SQLite 无 `information_schema` 近似行数），列元数据经 `TushareTableMapper.tableInfo` 执行 `PRAGMA table_info`——查询层同样走 MyBatis，无 `JdbcTemplate` 直连。

驱动与连接：`org.xerial:sqlite-jdbc 3.50.3.0` 由 Hikari 连接池（8 连接）持有；URL 参数 `journal_mode=WAL&busy_timeout=5000&date_class=TEXT&foreign_keys=on&synchronous=NORMAL` 决定驱动行为——其中 `date_class=TEXT` 与 `SqliteLocalDateTimeTypeHandler` 的文本时间戳口径一致，`busy_timeout` 是单写者锁之外的第二道 `SQLITE_BUSY` 防线。

### 4.2 能力单元框架 `capability-core`（全系统核心）

落地《核心能力体系设计详案》的三层执行架构。设计目标一句话：**框架骨架写一次基本不动，业务单元像插件一样持续增加，且每加一个单元不改任何框架代码。**

#### 4.2.1 包边界与依赖方向

依赖铁律：**只能 `units → runtime → spi`，绝不反向。** runtime 不 import 任何具体单元；units 之间禁止互相调用（单元协作只通过 FactBundle 传递，由流水线编排）。这条边界保证单元可独立测试、可独立升版、可按流水线自由组合。

包结构与资源目录一一对应（约定即配置，见第 3 章）：`prompts/{unit_id}/v{X}.md`（L2 提示词，随单元版本冻结）、`schema/{unit_id}-v{X}.json`（L2 输出 Schema）+ `.rules.json`（单元校验规则）、`golden/{unit_id}/`（黄金样本：输入快照 + 人工确认的期望输出）。

#### 4.2.2 SPI 定义

```java
public interface CapabilityUnit {
    String unitId();          // 如 calc_valuation_percentile
    String version();         // v1.0，与 SPEC front-matter 一致
    UnitType type();          // COMPUTE / INTERPRET
}

public interface ComputeUnit extends CapabilityUnit {
    // scope（BATCH / PER_STOCK）由 @CapabilityUnit 注解声明，Runner 启动期校验阶段类型与 scope 匹配：
    //   BATCH——一次执行处理整个标的池（M1 全部 compute 单元均为 BATCH），签名如下，
    //           产出批量落 unit_fact
    BatchFactResult computeBatch(FactContext ctx, StockPool pool);
    //   PER_STOCK——逐标的执行；FactBundle 是 per-stock 视图，S3 入口从本地表装配
    FactResult compute(FactContext ctx);
    // 确定性计算：同输入必同输出，可单测
}

public interface InterpretUnit extends CapabilityUnit {
    InterpretResult interpret(FactBundle facts);
    // InterpretResult = { reportMd, judgmentBlock(JSON) }
    // degraded 工厂方法：由框架（非 LLM）按判断 Schema 生成机械 judgmentBlock，
    // 使 emitJudgment 对正常/降级结果走同一条消费路径
}
```

- **单元注册**：Spring Bean 标注 `@CapabilityUnit` 启动期扫描进 `UnitRegistry`；版本号同步写入 `unit_version` 表，与方法版本快照联动；
- `modelProfile`（fast / strong，见 6.4 成本分层）由 `@CapabilityUnit` 注解声明，`UnitRegistry` 启动期统一读取——接口不暴露 `modelProfile()`，避免与注解双源不一致。

#### 4.2.3 compute 单元：批量粒度的纯函数

compute 单元的本质是**纯函数**：`(FactContext, 标的池, 参数) → BatchFactResult`。**M1 全部 compute 单元均为 BATCH 粒度**（一次执行处理整个池，如全市场过滤、全池分位计算），因为其数据访问天然是集合运算（SQL/批量取数），逐标的循环反而是反模式。实现范式是「实现一个接口的类」，不继承任何框架基类，不注入 LLM，不起事务：

```java
@CapabilityUnit(id = "calc_valuation_percentile", version = "v1.0", type = COMPUTE, scope = BATCH)
public class CalcValuationPercentileUnit implements ComputeUnit {

    private final DailyBasicRepository dailyBasicRepo;   // 只依赖数据仓储

    @Override
    public BatchFactResult computeBatch(FactContext ctx, StockPool pool) {
        // ctx 提供：trade_date、RunId（日志贯穿用）
        // 1. 从本地表按池分页/流式批量取数（只读，禁止在本单元内触发远端拉取——数据就绪是 S0 数据门的职责）
        // 2. 逐标的纯函数计算（commons-math3 算经验CDF分位、分档），批内分页处理，DB 连接友好
        // 3. 组装 BatchFactResult（逐标的含 data_status 与 notes，缺失显式标注），批量落 unit_fact
    }
}
```

实现约束（单元开发 code review checklist）：
1. **确定性**：同输入必同输出，内部禁止 `LocalDate.now()`（时间一律取 `ctx.tradeDate`），禁止调 LLM、禁止调 Tushare 远端；
2. **无状态**：单元类可以做成单例 Bean，所有状态在 `BatchFactResult` 里；
3. **显式降级**：数据不足不是抛异常，而是返回 `data_status=degraded` + 原因——降级是输出的一部分，不是异常（对应能力详案 5.7）；
4. **批量纪律**：对池分页/流式处理，禁止一次性加载全市场到内存；并发度受 DB 连接池约束（单元级并行，非标的级无限制并行）；
5. **测试**：纯 JUnit 单测即可（不起 Spring）。

#### 4.2.4 LLM 调用分层与 interpret 单元模板

项目中存在两类性质不同的 LLM 调用，基础设施对应分三层，上层复用下层：

| 调用类别 | 例子 | 产出 | 要求 |
|---|---|---|---|
| 判断生产类（流水线能力单元） | 个股解读、多空对撞、异动归因 | 报告 + **结构化判断块（进 judgment 表）** | 完整生命周期：三重校验、带错重试、降级、黄金样本 |
| 报告生成类（系统级任务） | 首页「今日一句话」、M3 归因报告、M4 周报/月报 | 叙述性文本（进 report，不进 judgment） | prompt 版本化 + 用量记账即可，无需判断校验 |

| 层 | 组件 | 固化内容 | 相比上层可省略 |
|---|---|---|---|
| 调用基座 | `LlmInvoker`（底层组件） | 重试/退避、超时、429 处理、token 用量记账（`llm_usage` 数据源）、run_id 日志贯穿 | — |
| 轻量模板 | `ReportGenerator` | prompt 版本化加载 + 调用基座 | 判断 Schema 校验、facts_used 比对、黄金样本回放、降级矩阵 |
| 完整模板 | `AbstractInterpretUnit` | 轻量模板全部 + 三重校验链 + 错误回喂重试 + 降级矩阵 + 黄金样本回放 | — |

> 命名约定：「调用基座/轻量模板/完整模板」是 **LLM 调用栈分层**，与「L1 计算/L2 解读/L3 结构化」的**执行层分层**是两个维度，禁止混用 L 编号称呼调用栈（避免与执行层冲突）。

两条铁律：
1. **进 `judgment` 表的调用必须走完整模板（AbstractInterpretUnit）**，没有例外——判断要进归因闭环，Schema 校验与版本冻结缺一不可；
2. **任何调用禁止裸调 `ChatClient`**，最低经过 `LlmInvoker` 调用基座——否则 token 花费脱离成本看板，prompt 脱离版本管理（无法回答「上周那句话是哪版 prompt 生成的」）。

完整模板（AbstractInterpretUnit）：LLM 调用的完整生命周期（加载 prompt → 组装输入 → 调用 → 解析 → 三重校验 → 带错重试 → 降级 → 产出报告+判断块）**在抽象基类里写一次**，业务单元只提供三个差异点：

```java
public abstract class AbstractInterpretUnit implements InterpretUnit {

    @Autowired protected ChatClient chatClient;          // 供应商无关（ADR-4）
    @Autowired protected PromptLoader promptLoader;      // 按单元版本冻结加载，
                                                         // 模板内容即能力详案第 5/6 章 Spec 的代码化
    @Autowired protected ValidationChain validationChain;

    // ---- 差异点 1：用哪个 prompt 与 schema（约定到资源目录）----
    protected abstract String promptId();      // "interpret_valuation" → prompts/interpret_valuation/v1.md
    protected abstract String schemaId();      // "interpret_valuation-v1.json"

    // ---- 差异点 2：给 LLM 喂什么（事实表裁剪，禁止喂原始数据）----
    protected abstract Map<String, Object> buildFactsPayload(FactBundle facts);

    // ---- 差异点 3：LLM 输出如何映射为强类型结果 ----
    protected abstract InterpretResult mapOutput(UnitRawOutput raw, FactBundle facts);

    // ===== 模板方法：生命周期固化，子类不得重写 =====
    public final InterpretResult interpret(FactBundle facts) {
        String prompt = promptLoader.load(promptId(), version());      // 按版本冻结加载
        Map<String,Object> payload = buildFactsPayload(facts);
        for (int attempt = 0; attempt <= MAX_RETRY; attempt++) {
            UnitRawOutput raw = callLlm(prompt, payload, attempt);     // 含超时/429退避
            ValidationResult vr = validationChain.validate(raw, facts, schemaId());
            if (vr.passed())  return mapOutput(raw, facts);
            payload.put("_last_validation_error", vr.errors());        // 错误回喂，模型自纠
        }
        return InterpretResult.degraded(facts, "schema validation failed after retries"); // 降级而非抛异常：
        // degraded 结果由框架（非 LLM）按判断 Schema 生成机械 judgmentBlock
        // （direction=neutral、confidence=低、degraded=true、有效期默认5个交易日、
        //   仅含一条到期重估 direction_fail 规则），emitJudgment 对正常/降级结果单路径消费
    }
}
```

子类因此薄到只剩「业务本身」。采用模板方法而非组合+策略的原因：LLM 调用生命周期**严格有序且不可跳步**（校验失败必须带错重试、重试耗尽必须降级），`final` 从语言层面禁止子类绕过骨架，策略模式做不到这种强制（ADR-10）：

```java
@CapabilityUnit(id = "interpret_valuation", version = "v1.0", type = INTERPRET,
                modelProfile = "fast")
public class InterpretValuationUnit extends AbstractInterpretUnit {
    // promptId/schemaId/buildFactsPayload/mapOutput 四个方法，
    // 内容就是能力详案 5.5（解读指令）与 5.6（质量要求）的代码化
}
```

#### 4.2.5 L3 校验链（责任链，顺序固定）

```java
ValidationChain = SchemaValidator          // JSON Schema 合法性（networknt）
                → FactsUsageValidator      // facts_used 与 FactBundle「指标名+数值」双比对：
                                           //   名不存在=编造，值不一致=篡改（相对误差>0.1%即失败，
                                           //   BigDecimal 数值语义比对 + unit 字段核对），两者都防
                → TagVocabularyValidator   // logic_tags ⊆ 受控词表
                → JudgmentRuleValidator    // 单元特有规则（如 stop_loss 校验，规则集见能力详案 6.5）
                → ReportNumberScanner;     // 报告正文中未被 [[metric|value]] 标记包裹的数值 token 一律失败
                                           //   （封死叙述文本绕过 facts_used 校验编造数字的旁路，能力详案 5.5）
```

- 每个校验器输出**结构化错误**（哪个字段、违反什么规则），直接回喂 prompt——比笼统的「校验失败」重试成功率高得多；
- 校验器按 schemaId 关联的规则集执行，`JudgmentRuleValidator` 的规则本身也是资源文件（`schema/{unit_id}-v{X}.rules.json`），升版即换文件；
- 链上所有校验器无状态、可单测——L3 是判断可信度的最后防线，测试优先级最高。

> **落地实现（T8）**：`capability.runtime.validation`（链契约 + `validators/` 五个校验器 + `rule/` 规则引擎）。
> 三条实现口径：①顺序由 `ValidationValidators` record 的字段位置固化，改顺序需同步本节；
> ②模型输出问题只返回 `ValidationError`，配置缺陷（Schema/规则集/词表缺失或非法）抛 **4005** fail-fast——
> 不允许「用坏配置静默放过所有判断」；③`SchemaValidator` 额外硬校验
> `unit_id/unit_version/stock_code/trade_date` 与本次执行一致（Schema 表达不了「等于当前版本」，而串标的/旧版本会污染存档）。
> 事实载荷的指标叶子约定为 `{"value": …, "unit": …}`（`FactMetrics` 摊平为 `parent.child` / `parent[i]`），
> 未声明 `unit` 的叶子被 `facts_used` 引用即判失败。

#### 4.2.6 FactBundle：单元间唯一通信介质

```java
public final class FactBundle {
    private final String tsCode, tradeDate, runId;
    private final Map<String, FactResult> facts;   // key = unitId，写入后不可变
    // 类型安全读取：facts("calc_valuation_percentile", ValuationFact.class)
}
```

约束：
- **单元协作只通过 FactBundle，禁止单元间直接方法调用**——这是「原子能力可自由编排」的代码级保障；
- FactResult 一律用 Java record（不可变），带自己的 Schema 版本号；
- **两段式生命周期**：builder 阶段（同阶段 parallel 单元并发写入，内部用线程安全结构，如 `ConcurrentHashMap`）→ 构建完成后 sealed 为 immutable 只读视图供下游消费。S1 全市场 5000 只 × 并行单元共享写同一个 bundle，非线程安全的 Map 在此必然出并发 bug，此约束为强制项；
- **装配时机**：FactBundle 是 per-stock 视图，在 S3 入口才从本地表装配（S1/S2 批量单元的事实已落 `unit_fact`，按 ts_code 组装）——BATCH 单元产出与 per-stock 视图经由此点衔接；
- **interpret 结构化摘要通道**：interpret 单元产出的「结构化摘要」（如业务概况的口径适配结论）作为一类事实写入 FactBundle，供同标的后续 interpret 单元的 prompt 引用（如估值解读消费业务速览结论）——这是 interpret 单元间**唯一**依赖通道，禁止引用全文，可用性由容器内串行执行顺序保证；
- 流水线 run 结束后 FactBundle 整体序列化落 `unit_fact` 表（溯源与事后排查），这是报告数字溯源弹层的数据源。**落库分层（控制单机 SQLite 库数据量）**：完整 payload 仅 REPORT_POOL 标的落库（永久保留，供报告溯源）；S1/S2 淘汰标的只把「各单元通过标志 + 评分/淘汰原因」摘要写入 `pipeline_run_item`，保留 90 天——满足「为什么没入选」的溯源需求，避免全市场 ~2.5 万行/天完整 payload 拖垮单机库。

#### 4.2.7 黄金样本回放

框架侧由 `GoldenSampleReplayer` 提供统一回放入口：interpret 单元维护 10~15 个人工确认样本，prompt/模型变更后回放，**另每周固定日 + 发版前周期性自动回放**（模型供应商会静默升级同名模型权重，此类漂移不触发「变更」事件，只能靠周期回放捕获）。样本管理与回归判定标准（漂移 1 档以内样本占比 ≥80% 通过等，见能力详案 5.8）。

#### 4.2.8 新增一个单元的标准动作（开闭原则验收）

以 M2 新增 `interpret_announcement_impact`（公告解读）为例，完整动作清单：

1. 写 `SPEC.md`（能力详案第 2 章 8 段式，含方法论来源登记）；
2. 新建 `units/interpret/InterpretAnnouncementImpactUnit`，继承 `AbstractInterpretUnit`，实现三个差异点方法；
3. 写 `prompts/interpret_announcement_impact/v1.md` + `schema/...-v1.json` + `.rules.json`；
4. 录 10 个以上黄金样本到 `golden/`（数量与回归判定标准见能力详案 5.8）；
5. 写单测（compute：纯函数用例；interpret：mock ChatClient 走模板方法回放）；
6. 在流水线 DSL 里挂载到对应阶段。

全程不修改 capability/runtime 任何一行——这是本框架的验收标准。目标效率：compute 单元半天内、interpret 单元一天内（不含方法论提炼）完成开发到测试。

#### 4.2.9 明确拒绝的实现方式（设计约束）

| 拒绝项 | 理由 |
|---|---|
| 绕过 LlmInvoker 裸调 ChatClient | 调用脱离用量记账与 prompt 版本管理；「今日一句话」这类小调用也必须走调用基座 |
| 把报告生成类任务伪装成 interpret 单元（挂空的 judgmentSchema） | 制造假判断、污染黄金样本与降级矩阵；报告类任务走轻量模板 ReportGenerator 即可 |
| prompt 存数据库、运行时热更 | prompt 是方法版本的一部分，必须随代码进 git、随版本冻结；热更会悄悄破坏判断的版本可溯性（总纲 5.2） |
| 规则引擎（Drools 等）做红旗/初筛规则 | 规则总量 < 50 条，Java + 配置参数足够；引入规则引擎的语言成本远超收益 |
| 单元间直接注入调用 | 破坏原子性，编排权必须只属于流水线层 |
| 通用「AI 分析器」（一个 prompt 走天下） | 与「标准化原子能力」定位相反；每个单元的 prompt/Schema/质量要求必须独立管理 |
| 在 compute 单元里做远端取数 | 数据就绪是 S0 数据门 + ingest 模块的职责；单元只读本地库，保证可测可重放 |

### 4.3 流水线引擎 `pipeline-engine`

**流水线定义（M1 用 Java DSL 代码定义，阈值/权重等参数走配置）：**

```java
PipelineDefinition P1 = Pipeline.of("P1", "标的发现与深度筛选")
    .stage("S0", gate(DataQualityGate::check))                    // 整线挂起型失败
    .stage("S1", parallel(UNIVERSE,                               // 批量compute单元：单元级并行，
            batchUnit("screen_universe_baseline"),                // 每个单元一次执行处理全市场（非per-stock）
            batchUnit("calc_trend_strength"),
            batchUnit("calc_growth_screen"),
            batchUnit("calc_valuation_percentile"),
            batchUnit("calc_key_levels")))
    .stage("S2", serial(FOCUS_POOL_OF(S1),                         // ~800 → ~30-50
            unit("screen_financial_redflag")))
    .stage("S3", perStockParallel(REPORT_POOL_OF(S2), 4,           // LLM并发限流=4
            unit("interpret_business_overview"),
            unit("interpret_fundamental_quality"),
            unit("interpret_valuation")))
    .stage("S4", perStockParallel(REPORT_POOL_OF(S2), 4,           // LLM并发限流=4，与S3共用信号量
            unit("interpret_bull_bear_collision")                  // 主判断生产者（标的间无数据依赖，禁止串行）
                .then(emitJudgment())))                            // L3校验+冻结存档（单标的动作，随标的并行）
    .stage("S5", serial(REPORT_POOL_OF(S2), unit("calc_composite_rank")))
    .downgrade(DOWNGRADE_MATRIX)                                   // 能力详案 7.3 降级矩阵
    .build();
```

> 粒度约定：L1 compute 单元均为 **BATCH 粒度**（`batchUnit`，一次执行处理整个池，产出批量落 `unit_fact`）；FactBundle 是 **per-stock 视图**，在 S3 入口才从本地表装配（S1/S2 批量事实已落表）。`scope` 由 `@CapabilityUnit` 注解声明，Runner 启动期校验阶段类型与 scope 匹配（parallel 池级阶段只接受 BATCH，perStockParallel 只接受 PER_STOCK）。

**编排要点：**

| 要点 | 设计 |
|---|---|
| DSL 只是声明，执行器统一解释 | `PipelineDefinition` 是纯数据结构（阶段列表+依赖+池引用），`PipelineRunner` 是唯一解释器——保证所有流水线共享同一套降级矩阵、日志、进度上报，没有第二条执行路径 |
| 阶段类型只有四种 | `gate`（整线门禁）/ `parallel`（池级批量单元并行，BATCH scope 专用）/ `perStockParallel`（每标的并行+信号量限流，PER_STOCK 专用）/ `serial`（串行）。Runner 启动期校验阶段类型与单元 scope 匹配。新场景优先用这四种组合，不够再加 |
| 标的池是一等公民 | 每阶段显式声明消费哪个上游池（`FOCUS_POOL_OF(S1)`），池的收缩过程本身就是流水线的可解释叙事，前端候选页的因子明细直接读池元数据 |
| parallel 阶段内单元必须无数据依赖 | 同一阶段 parallel 编排的单元之间禁止存在事实依赖（依赖必须跨阶段表达）——parallel 不保证单元间执行顺序，隐式时序依赖是并发 bug 之源；编排时按数据依赖图分阶段 |
| emitJudgment 是显式阶段动作 | 主判断的产出不是 LLM 单元的副作用，而是 S4 阶段显式编排的动作（校验→冻结→存档），保证「判断存档」这个核心资产永远走同一条受控路径 |
| S4 禁止串行执行 | 主判断生产标的间无数据依赖，必须走 `perStockParallel(4)`：30~50 只重点池串行执行 strong 档调用（单次 60~120s）需 50~100 分钟，叠加 S3 后会击穿 2h 总时长上限 |

**执行与状态：**

| 机制 | 设计 |
|---|---|
| 状态持久化 | `pipeline_run`（一次运行）+ `pipeline_run_item`（每只标的每阶段状态），支持断点查看与事后排查；运行中进度实时可查（前端看板数据源） |
| 重启恢复 | 应用启动时扫描 RUNNING / RETRY_WAIT 状态 run → 标 `INTERRUPTED`；run_item 粒度断点支持续跑（已 DONE 的标的/阶段直接跳过，复用幂等重跑规则）——无人值守场景的必要设施，否则 JVM 重启后 run 永久卡在 RUNNING |
| 运行互斥 | 同一 `pipeline_id` 同时只允许一个 RUNNING run；运行中收到重复触发（定时/手动）直接拒绝并在看板提示，杜绝双 run 并发写同一 trade_date 破坏 superseded 语义 |
| 失败语义 | 两种失败级别：**整线级**（S0 不达标 → run 置 RETRY_WAIT，写延迟 30 分钟的 trigger 复用轮询机制断点续跑，至 22:00 仍不达标挂起告警；不占执行线程睡眠）；**标的级**（单只 L3 校验失败 → 降级仅事实存档 + 生成机械降级判断 `degraded=true`，保证进入流水线3 链路，M3 统计默认过滤）——与能力详案 7.3 降级矩阵一一对应。流水线总时长上限 2h **不含 S0 等待重试窗口**，只计实际执行时间 |
| 并行控制 | 每标的 interpret 用虚拟线程 + `Semaphore(4)` 限制 LLM 并发（控成本、控供应商限速）；S1 批量 compute 单元为**单元级并行**（5 个单元同时执行），单元内部对池**分页/流式读取**，并发度受 DB 连接池约束——禁止「全市场全并行」式无限制并发打爆连接池 |
| 池变更权 | 只有 `screen_*` 单元可改变池成员，`calc_*` 单元只附加事实；Runner 启动期按此规则校验编排合法性，保证「池收缩过程可解释」的叙事不被破坏 |
| 幂等重跑 | 同一 `trade_date` 重跑：旧判断整行不覆盖，置 `superseded=1` + `invalidated_at`，插入新版本记录（judgment_id 带重跑序号）；已被流水线3 归因引用过的判断不允许自动重跑覆盖，走人工标注失效。`unit_fact` 事实允许新 run 覆盖（事实可重算），与 judgment 冻结形成对比语义 |

### 4.4 判断与验证模块 `judgment`

M1 只做存档与查询；M3 在同一模块内扩展验证扫描。

| 组件 | 设计 |
|---|---|
| 判断存档 | 主判断（能力详案 3.2 Schema）存 `judgment` 表（JSON 列），生成 `judgment_id` 即**冻结不可改**；`judgment_unit_ref` 记录 `units_used` + 各单元版本，是归因定位的钥匙 |
| 词表管理 | `logic_tag_dict` 受控词表，新增需人工确认并纳入方法版本快照 |
| VerificationScanner（M3） | 每日盘后巡检 `verification_rules` 四类规则（price_touch/price_break/direction_fail/logic_invalid）与最新日线比对，命中 → 生成待归因记录；依赖 `daily` + `index_daily`（基准），巡检排在 P1 流水线完成之后（数据就绪才巡检）。**规则状态机**：每条规则 `PENDING → TRIGGERED → RESOLVED`，命中即置 TRIGGERED 并只生成一次待归因记录（防价格在价位附近震荡导致重复归因）；**同日多规则命中合并为一条待归因记录**（携带全部触发原因，一次归因流程处理）。到期判定：`expire_at` 为自然日，到期后首个交易日巡检触发 direction_fail。**除权除息日**（依据除权数据）自动将存续判断的价位类规则置失效并触发重估，禁止用复权价与历史 key_levels 直接比对 |
| 归因支持（M3） | 按 `logic_tag` 分组命中率、按单元版本分组方向正确率、按偏差类型分布三个统计口径（能力详案 9.2） |

### 4.5 报告存档模块 `report`

- 报告 markdown 落盘 `/data/refine-loop/reports/{YYYYMMDD}/{ts_code}.md`，`report` 表存元数据（路径、run_item 关联、生成时间、报告标题）；
- 前端按需读取渲染（不做在线编辑；报告是产物不是工作区）；
- 选择磁盘而非数据库存正文：可 `grep`、可备份、可人工直接阅读，符合单人使用习惯。

### 4.6 版本管理模块 `method-version`

| 对象 | 存储 |
|---|---|
| 能力单元版本 | `unit_version` 表 + SPEC 文件 front-matter，注册时校验一致 |
| 方法版本快照 | `method_version` 表：当前版本号 + 下属单元版本清单 + 评分权重 + 受控词表版本，JSON 快照整体冻结 |
| 变更记录 | `method_version_changelog` 表：每次升版一行（改了什么/为什么/操作时间），即总纲 5.4 人工迭代的最小记录单位 |
| 绑定规则 | 判断存档时快照 `method_version`；旧判断存续期内禁止修改其关联版本（能力详案 9.1） |
| 一致性强校验 | PipelineRunner 启动期校验：当前 UnitRegistry 中各单元实际版本组合 **必须等于** 当前 `method_version` 快照登记的组合，不一致拒绝运行流水线并告警——防「只升单元版本、忘记生成方法版本快照」导致归因分组键失真 |

### 5.2 核心表结构要点

```sql
-- 判断表（本项目核心资产，总纲 5.1；SQLite 方言，与 db/schema.sql 一致）
CREATE TABLE IF NOT EXISTS judgment (
  -- [原 MySQL 表注释] 判断层-判断存档（同组仅一行 superseded=0，由生成列 + uk_judgment_active 保证）
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  judgment_id    VARCHAR(40)  NOT NULL,              -- J-20261122-P1-0001
  trade_date     CHAR(8)      NOT NULL,
  ts_code        VARCHAR(12)  NOT NULL,
  pipeline_id    VARCHAR(8)   NOT NULL,
  report_id      BIGINT       NOT NULL,
  method_version VARCHAR(20)  NOT NULL,
  direction      VARCHAR(16)  NOT NULL,              -- 冗余列，供SQL统计（bullish等）
  horizon_days   INT          NOT NULL,
  expire_at      DATE         NOT NULL,
  confidence     VARCHAR(4)   NOT NULL,
  payload        TEXT         NOT NULL,              -- 能力详案 3.2 完整Schema（JSON 文本，JSON1 可查）
  frozen         TINYINT      NOT NULL DEFAULT 1,    -- 存档即冻结（内容不可改）
  superseded     TINYINT      NOT NULL DEFAULT 0,    -- 同日重跑产生新版本时，旧记录置1
  active_flag    TINYINT GENERATED ALWAYS AS (CASE WHEN superseded = 0 THEN 1 ELSE NULL END) STORED,
  invalidated_at DATETIME     NULL,                  -- 唯一允许的更新列
  created_at     DATETIME     NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE UNIQUE INDEX IF NOT EXISTS uk_judgment ON judgment (judgment_id);
CREATE UNIQUE INDEX IF NOT EXISTS uk_judgment_active ON judgment (ts_code, trade_date, pipeline_id, active_flag);  -- 数据库级保证同组仅一行 superseded=0（置1后为NULL不参与唯一约束）
CREATE INDEX IF NOT EXISTS idx_judgment_active ON judgment (trade_date, ts_code, pipeline_id, superseded);
CREATE INDEX IF NOT EXISTS idx_judgment_expire ON judgment (expire_at, frozen);
CREATE INDEX IF NOT EXISTS idx_judgment_direction ON judgment (direction, method_version);
```

> 索引命名遵循《开发规范 02》§8.1：`uk_<表名>[_<用途>]` / `idx_<表名>[_<用途>]`（2026-11-24 由 `uk_active`/`idx_expire` 等更名）。

设计要点：
- `direction / confidence` 等高频统计字段从 JSON 冗余为列，避免 M3 效果统计全表 JSON 解析；
- JSON 语义列在 SQLite 中存 TEXT（可用 JSON1 函数查询），需要时配合表达式索引按需追加；
- 所有 JSON 载荷（unit_fact.payload / judgment.payload）在应用侧序列化/反序列化：当前数据接入与运维 API 的读写全部经 MyBatis Mapper（`data` 包），JSON 语义列（如 `quality_check_log.items`）以 String 承载、应用侧序列化（`QualityCheckLogStore` 用 Jackson；实体不建 JSON TypeHandler）；T6+ 业务表可用 MyBatis-Plus JSON TypeHandler + Java record 映射；
- SQLite 无表/列 COMMENT 与 `ON UPDATE CURRENT_TIMESTAMP`：原注释以 `-- [原 MySQL 表注释]` 行保留在 schema 中，更新时间由应用显式写入。

## 6. 关键机制专项设计

### 6.1 LLM 调用与结构化输出（可靠性关键）

```
InterpretUnit 执行模板（模板方法模式，业务单元只写 prompt 与输出映射）：
1. PromptTemplateLoader 按单元版本加载模板，注入 FactBundle 序列化 JSON
2. ChatClient 调用（system=prompt模板，user=事实表JSON）
3. 解析响应为 JSON（容错：剥 ```json 围栏）
4. 三重校验：JSON Schema 合法性 → facts_used 与 FactBundle「指标名+数值」双比对 → logic_tags 词表比对
5. 校验失败 → 把具体错误附回 prompt 重试（≤2 次）
6. 仍失败 → 降级：仅事实表存档 + pipeline_run_item 标记 + 告警
```

配置要点：
- `temperature` 按单元固定写死在 spec（解读类 0.2~0.4，对撞类 ≤0.5），纳入单元版本管理；
- 禁止依赖供应商「自动修复 JSON」特性，校验闭环必须本地闭环（供应商无关）。

### 6.2 调度与触发

| 触发类型 | 实现 |
|---|---|
| 定时 | `@Scheduled(cron="0 30 17 * * ?", timezone="Asia/Shanghai")` → 先查缓存交易日历，非交易日直接返回 |
| 事件触发 | 写 `pipeline_trigger` 表（M2 异动检测产生），每分钟轮询消费，消费即置 DONE；trigger 支持延迟执行（`execute_at` 字段，轮询只消费到期行）——S0 延迟重试复用此机制 |
| 手动重跑 | 前端触发 → 同表，带 `force=true` 标记走幂等重跑规则；已有 RUNNING run 时拒绝重复触发（运行互斥） |

单实例下 `@Scheduled` 单线程池即可；流水线执行占独立线程池（虚拟线程）。

**S0 数据门不达标的行为**：不直接挂起等人工——当前 run 置 RETRY_WAIT 并写一条 `execute_at=+30min` 的延迟 trigger（不占执行线程睡眠），到期断点续跑重查落库完整性（Tushare 数据晚披露属常态），至 22:00 仍不达标才整线挂起并告警（能力详案 7.1/7.3 同步）。流水线总时长上限 2h 不含 S0 等待窗口。

**告警通道**（无人值守盘后场景的必要设施）：可配置 webhook 通知，`application-prod.yml` 配置——**默认 Server酱**（微信推送，一个 token 即可），可切换飞书群机器人 / SMTP 邮件。触发场景：S0 挂起、流水线失败或超 2h 上限、L3 连续降级超阈值、LLM 日预算熔断、ingest 作业 FAILED、方法版本一致性校验失败。两条纪律：**① 聚合去重**——同 run 同类告警合并为一条摘要推送（如 40 只标的连环降级只发一条汇总，防告警风暴）；**② 心跳简报**——流水线正常完成后也推送一条完成摘要（候选池数量、降级计数、LLM 用量），**当天没收到心跳 = 系统异常**（JVM 挂掉/服务器宕机时所有依赖应用的告警都会失效，心跳是唯一的「反向告警」）。无外部组件，纯 HTTP 调用，符合成本约束。

### 6.3 限流与重试（外部调用纪律）

| 外部依赖 | 纪律 |
|---|---|
| Tushare | 限流器阻塞等待（40203 之前就拦住）；网络错误指数退避重试 3 次；`50101` 参数错误不重试直接告警 |
| LLM API | 供应商限速 429 → 令牌桶退避；单标的超时上限 120s；流水线总时长上限 2h，超限挂起告警 |

### 6.4 成本控制（个人预算约束）

| 措施 | 说明 |
|---|---|
| 模型分层 | `model_profile`：S1 全市场初筛纯代码零 LLM 成本；S3 速览/财务解读用 fast 档（如 qwen-flash / deepseek-chat）；S4 多空对撞用 strong 档。profile→模型映射在配置文件，换模型改配置 |
| 并发限流 | Semaphore(4) 控 LLM 并发，防突发账单 |
| Token 预算 | 每单元估算单次调用 token 量写入 SPEC；pipeline_run 结算当日实际调用量与费用估算，落 `ingest_log` 同级的 `llm_usage` 表，前端看板可见 |
| 日预算熔断 | 可配置单日 LLM 费用/token 上限（`llm_usage` 实时累计）：超限中止流水线剩余 LLM 调用（S3/S4 未执行标的保留待人工重跑），已完成的标的与判断正常保留，熔断即告警——防 prompt 异常循环（如错误回喂导致输入膨胀）烧穿月度预算 |
| 数据精简 | interpret 输入只给事实表不给原始 K 线（架构原则本身即省钱） |

### 6.5 本地缓存策略（Caffeine）

| 缓存对象 | Key | 容量/TTL | 失效方式 |
|---|---|---|---|
| 交易日历 | 全量 | 全量/7天 | 每周一定时刷新 |
| 股票列表 | 全量 | 全量/1天 | 盘后 ingest 完成后主动失效 |
| 申万行业映射 | 全量 | 全量/1天 | 同上 |
| 受控词表 | 词表版本 | 全量/无TTL | 版本变更主动失效 |
| 当前方法版本 | - | 1条/无TTL | 升版主动失效 |
| 报告内容 | report_id | 100条/30分钟 | 自然过期 |

原则：**只缓存参考数据，不缓存业务事实**（事实走 unit_fact 表，保证可溯源）。

**落地方式（2026-11-24 补齐公共基础设施）**：

| 层面 | 实现 | 说明 |
|---|---|---|
| 具名缓存 | `common.constant.CacheNames` + `common.cache.CacheSpec` | 上表每一行对应一个 `CacheSpec`：TTL/容量/说明集中登记，`CacheConfig` 逐个装配 Caffeine（`recordStats()` 可观测）。`@Cacheable(cacheNames = CacheNames.XXX)` 只负责「用哪个缓存」 |
| 编程式 | `common.cache.CacheTemplate` | 注解表达不了的场景（多表拼装、条件缓存、主动失效），空值安全、加载失败不写缓存 |
| 方法级临时缓存 | `@LocalCache` / `@LocalCacheEvict` | 不宜登记为全局缓存的短 TTL 场景；同 key 并发单飞（防击穿），`null` 也被缓存 |
| 观测与运维 | `GET /api/common/cache`、`DELETE /api/common/cache/{name}` | 命中率/淘汰数/容量；数据重建后按需清空，不用重启 |
| 纪律 | 同类自调用不走代理、只能代理 public 非 final 方法 | 失效要与数据变更动作成对出现（`@CacheEvict` / `@LocalCacheEvict`），不能只靠 TTL 兜底 |

## 8. 部署方案（单服务器）

### 8.1 首选：裸机 systemd（最简）

```
构建（本机）：
  后端   mvn -Pprod package        → refine-loop.jar
  前端   npm run build             → dist/
发布：
  scp refine-loop.jar server:/opt/refine-loop/
  scp -r dist/*          server:/var/www/refine-loop/
  ssh server "systemctl restart refine-loop && systemctl reload nginx"
```

systemd 服务要点：`ExecStart=/usr/bin/java -Xmx1g -Xss512k --enable-preview=false -jar /opt/refine-loop/app.jar`，`Restart=on-failure`，配置文件外置 `application-prod.yml`（含 Tushare token、LLM key，权限 600，**禁止入库与进仓库**）。生产库为 SQLite 单文件库（默认 `/data/refine-loop/db/refine_loop.db`，可用 `DB_URL` 覆盖），首次启动由 `SqliteSchemaInitializer` 自动创建目录、执行 schema 建表，**无需安装/初始化数据库服务**。

### 8.2 备选：docker-compose（若想要环境一致性）

单 compose 文件两服务（app + nginx；SQLite 随应用容器卷持久化，不再需要 mysql 容器）。仅当裸机方案出现环境问题时启用，非默认路径。

### 8.3 运维例行

| 事项 | 方案 |
|---|---|
| 数据库备份 | cron 每日 02:00 备份 SQLite 库文件到 `/data/backup/`，保留 14 天：优先 `sqlite3 refine_loop.db "VACUUM INTO '/data/backup/refine_loop-$(date +%F).db'"` 生成一致性快照；若直接复制文件，须先 `PRAGMA wal_checkpoint(TRUNCATE)` 并同时纳入 `-wal`/`-shm` |
| 数据库初始化/升级 | 启动期 `SqliteSchemaInitializer` 自动执行 `db/schema.sql`（全部 `IF NOT EXISTS`，幂等补表/索引）；开发期 schema 变更删库文件重建，生产升级同样只补结构、不做数据迁移（ADR-7） |
| 过期数据清理 | 每日定时清理：`pipeline_run_item` 中淘汰标的的事实摘要超 90 天删除（REPORT_POOL 标的记录永久保留）；`rate_limit_counter` 明细超 30 天删除 |
| 报告备份 | 每周日 tar 全量月度目录，保留 90 天 |
| 异地容灾 | 判断表是核心资产且不可再生，本机 14 天备份窗口不足以抵御单盘故障：每周将 SQLite 库文件快照与 reports 目录同步至对象存储（OSS/COS，月成本元级）或第二块磁盘 |
| 日志 | Logback 按天+按大小滚动，保留 30 天 |
| 观测 | 前端看板即主观测面；辅以 `pipeline_run` / `llm_usage` / `rate_limit_counter` 表 |

## 10. 关键架构决策记录（ADR 摘要）

| # | 决策 | 理由 | 放弃的方案 |
|---|---|---|---|
| 1 | 单体单模块，按领域分包 | 单服务器/单人/低成本；包边界预留拆分可能 | 多 Maven 模块（构建复杂度不值）、微服务（完全不值） |
| 2 | MyBatis-Plus（2026-11-24 由「保留依赖」修订为 **ORM 主框架**） | 业务表实体 + `BaseMapper` + `LambdaQueryWrapper`；41 表批量 upsert 幂等写入（SQLite `ON CONFLICT ... DO UPDATE`）由 MyBatis 动态 SQL Provider 承载；批量走 MyBatis BATCH 执行器。原 T2~T5「`JdbcTemplate` 元数据驱动写入器」方案已被 ORM 化取代（D13 / ADR-12） | JPA（upsert 别扭） |
| 3 | `@Scheduled` + 触发表 | 单实例无分布式需求，状态进 SQLite 可查可手动补跑 | Quartz（过重）、XXL-Job（多一个组件） |
| 4 | Spring AI 双协议核心库 | 业务代码供应商无关；OpenAI 兼容（方舟 Coding Plan / DeepSeek / DashScope 兼容 / 自建）与 Anthropic Messages（Claude / 自建网关）一套代码切换；T7 起不再绑定 DashScope starter | 直接绑 SDK、starter 单协议锁定 |
| 5 | 报告正文落磁盘不进库 | 可 grep、易备份、报告是产物非数据 | 报告存表（JSON 膨胀） |
| 6 | 虚拟线程做每标的并行 | LLM 调用是 IO 密集，Java 21 原生支持零框架成本 | WebFlux（调试成本）、CompletableFuture 链（可读性差） |
| 7 | 原生 SQL 脚本一次性建表，不引入迁移工具 | 单机单库（SQLite 单文件）、一次性上线：开发期 schema 随代码自由调整，无存量数据需要迁移；判断表不可变约束由代码层保障（UPDATE 仅允许 superseded/invalidated_at 两列），不依赖迁移工具 | Flyway（对无迁移需求的单机项目是多余复杂度）、散落各处的手工建表（漂移风险） |
| 8 | 判断 JSON 载荷 + 统计列冗余 | 完整结构存 JSON 保证 Schema 演进自由；高频统计字段冗余为列保证 M3 统计效率 | 全列展开（Schema 变更即迁移）、全 JSON（统计低效） |
| 9 | capability 框架采用轻量插件化 + 模板方法，单元以 Spring Bean 注册 | 需要的是开闭原则（对扩展开放、对修改关闭）而非运行时热插拔；新增单元 = 一个类 + 一个 prompt 目录，零改框架；编译期类型安全 | 按模块直写（生命周期逻辑复制 N 份）、重量级插件化（类加载隔离成本不值）、元数据驱动一切（演化成「在配置里写代码」） |
| 10 | interpret 生命周期用模板方法（final 骨架）而非组合 + 策略 | 生命周期严格有序且不可跳步，语言层禁止子类绕过骨架，对应「流程标准化」要求 | 策略/组合（无法强制有序流程） |
| 11 | 数据库引擎 SQLite 3（2026-11-24 由 MySQL 8 迁移） | 单机个人系统：零安装零运维、单文件备份、测试与生产同引擎可真实验证；SQL 集中在 MyBatis Mapper/Provider 层 + 注册表驱动，若未来数据量/并发上来可替换回 MySQL（仅需 schema 与少数方言点） | MySQL 8（需独立服务进程/账号/备份工具）、H2（仅内存测试、与生产不同引擎） |
| 12 | 数据访问层 ORM 化（MyBatis-Plus 真正落地，2026-11-24） | 用户指出「ORM 不是 MyBatis 吗，怎么直接用 JdbcTemplate」：依赖只登记未使用、SQL 散落 service 且绕过实体/参数映射/类型处理器，与 §1 选型不符。方案：① 业务表 MyBatis-Plus 实体 + `BaseMapper` + `LambdaQueryWrapper`（`ON CONFLICT` 注解 upsert、原子累加）；② 41 张镜像表保留「元数据驱动」但改由 MyBatis 动态 SQL Provider 承载（不写 41 份 XML/Mapper，避免与注册表 `fields` 漂移——原 D2 决策的延续）；③ 批量写统一 `MyBatisBatchExecutor`（BATCH，500 行/批）；④ DDL 用 `ScriptRunner`、`PRAGMA` 走 Mapper。结果：**生产代码 0 处 `JdbcTemplate`**（仅测试夹具） | 41 张表逐表手写 Mapper/XML（维护成本高、与注册表字段漂移）；继续 `JdbcTemplate`（偏离技术选型、SQL 散落业务层） |
