## 1. 三层执行架构

### 1.1 设计约束

参考插件 skill 全部是**纯提示词框架**：AI 直接看数据自由判断，无计算逻辑、无数据契约、输出是散文而非结构化结论。直接照搬会导致判断不可复现、无法量化归因（流水线3 失效）、无人值守时无法做数据质量校验（总纲 5.5）——与总纲「标准化流程、结果可靠」的定位直接冲突。因此每个原子能力单元不是「一个 skill」，而是三层组合：

```
┌─────────────────────────────────────────────────────────┐
│ L1 计算层（纯代码，无 LLM）                                │
│   输入：本地库已落库的 Tushare 数据（41 张表）               │
│   职责：指标计算、阈值判定、分位排名、异常标记                │
│   输出：结构化「事实表」（JSON，含原始数值 + 计算口径）        │
│   要求：确定性、可单测、同输入必同输出                        │
├─────────────────────────────────────────────────────────┤
│ L2 解读层（LLM，方法论来自 skill 提炼）                     │
│   输入：L1 事实表（只喂计算结果，不喂原始行情）               │
│   职责：解读、综合、多空对撞、生成叙事报告                    │
│   输出：报告（markdown）+ 结构化判断块（按第3章 Schema）      │
│   要求：禁止编造事实表中不存在的数字；缺失必须显式标注          │
├─────────────────────────────────────────────────────────┤
│ L3 结构化层（契约 + 校验器，系统代码）                       │
│   职责：校验 L2 输出的判断块 Schema 合法性；                 │
│         附加 method_version / units_used 等元数据；         │
│         与报告关联存档，供流水线3 消费                       │
│   要求：校验失败重试（最多 2 次），仍失败则降级存档并标注       │
└─────────────────────────────────────────────────────────┘
```

### 1.2 单元类型定义

| 类型 | 组成 | 示例 | LLM 参与 |
|---|---|---|---|
| `compute` | 仅 L1 | 估值分位计算、趋势强度计算 | 否 |
| `interpret` | L1（轻量取数）+ L2 | 业务速览、多空对撞 | 是 |
| `pair` | compute 单元 + interpret 单元配对使用 | 估值分位计算 → 估值解读 | 是 |

规则：
- **凡是能用代码算的，一律不进 LLM**（如均线、分位、阈值触发）；
- interpret 单元的输入必须是 L1 产出的结构化事实表，禁止把原始 K 线数组直接丢给 LLM 自行计算；
- 每个单元独立版本号（`unit_id@vX.Y`），判断记录必须记录所用单元版本清单（见 3.2）。

### 1.3 流派锁定原则（方法论一致性约束）

参考插件混用了多个流派（Minervini 趋势派、价值派、游资情绪派）。总纲 5.3 的「方法因素」归因要求**同一判断的分析方法必须稳定**，否则偏差无法定位到方法缺陷。因此：

- **M1 主流派锁定为「成长 + 趋势」混合流派**（CANSLIM / VCP / PEAD 体系，与流水线1 的选股定位一致），所有单元的方法论提炼均以此为唯一来源；
- 价值派（DCF、护城河）与情绪派（连板接力）skill 仅做交叉验证视角，不进入判断主链路；
- 流派属于方法版本的一部分：切换流派 = 新方法版本，需走人工迭代闸门（总纲 5.4）。

## 2. 能力单元标准 Spec 模板（8 段式）

每个原子能力单元必须按以下 8 段编写 Spec，缺一不可。第 5、6 章是照抄模板。

```markdown
### 单元定义
- unit_id / 名称 / 类别（六大类）/ 类型（compute|interpret|pair）/ 版本
- 所属流水线 / 执行时机

### ① 方法论来源
- 参考 skill 及提炼内容（哪些 Step、哪些质量要求被采纳）
- 流派标注

### ② 输入数据契约
- 来源表（对应 Tushare 手册表名）、字段、口径、时间窗
- 缺失/过期处理（显式标注，禁止编造——总纲 5.5）

### ③ 计算规范（compute 必有）
- 指标定义与公式、参数（窗口、阈值）、边界规则
- 输出事实表 Schema

### ④ 解读规范（interpret 必有）
- 输入事实表、LLM 核心指令（提炼自 skill 的执行流程）
- 报告模板、禁止事项

### ⑤ 结构化输出契约
- 判断块字段（引用第 3 章 Schema，定义本单元贡献的维度）

### ⑥ 质量要求
- 提炼自 skill 的「质量要求」段 + 本项目补充

### ⑦ 失效与降级
- 数据缺失、限流、Schema 校验失败时的行为

### ⑧ 测试要求
- compute：单测覆盖正常值/边界/缺失；interpret：黄金样本回放
```

### 3.3 契约约束（不可违反）

1. **四类验证规则**（`price_touch` / `price_break` / `direction_fail` / `logic_invalid`）与总纲 4.2 流水线3 的「价位偏离、方向偏离、逻辑失效、到期验证」一一对应，`verification_rules` 是流水线3 巡检的唯一触发依据；
2. `logic_tags` 必须来自**受控词表**（随方法版本维护，初始约 40 个标签），禁止自由发挥——归因时按标签聚类才能统计「哪类逻辑最常出错」；
3. `facts_used` 只允许引用 L1 事实表中存在的指标名，校验器比对事实表做硬校验，**杜绝编造数字**（总纲 5.5 的机器化落地）；
4. `units_used` + `method_version` 是归因定位「方法因素」的钥匙：统计效果时按版本分组（总纲 5.2）；
5. 判断记录不可删除、不可改写，仅可标注失效（总纲 5.1），主判断一经存档生成 `judgment_id` 即冻结（「冻结」指**内容不可改**；同 `trade_date` 重跑时插入新版本记录、旧记录标注失效并置 `superseded`，不允许 UPDATE 覆盖内容）；
6. `key_levels` 中所有价位（support/resistance/stop_loss）统一采用**不复权价格**口径，与 `daily` 表原始收盘价同口径；验证巡检遇除权除息事件时，按 `adj_factor` 比例调整价位后继续验证，只有比例偏差超过 3% 才置失效并触发重估，禁止直接用复权价与历史价位比对、也禁止每逢分红即废掉价位规则；
7. 主判断必须在存档时固化 `benchmark`（基准指数 + 申万一级行业代码 + 行业指数代码 + 成分口径日期 + 收益算法），M3 归因定量拆解直接消费该字段——禁止归因时按 stock_basic 事后映射（行业归属会随时间变动，导致归因基准漂移）；
8. 验证规则自带状态机：`PENDING → TRIGGERED → RESOLVED`，另有旁路终态 `EXPIRED`（到期未触发）/`INVALIDATED`（除权或人工失效）/`SUPERSEDED`（判断被取代）；一条规则只触发一次待归因记录；同日多规则命中合并为一条待归因记录（携带全部触发原因）；
9. `facts_used` 数值比对必须按 `BigDecimal.compareTo` 数值语义执行（禁止字符串比对），指标值一律携带 `unit` 字段（pct/元/倍等），单位不一致视为校验失败——防浮点表示差异与百分比口径造成误判或漏判；数值允许按模型书写精度做最后一位四舍五入（18.5432→18.5 通过，→18.9 失败）；
10. **有效期统一为交易日**：`direction.horizon_days` 的单位由 `horizon_unit="trading_days"` 显式声明，`expire_at` 只由交易日历计算（`TradeCal`），判断块自报的 `expire_at` 若与计算结果不一致即拒绝存档；日历不足时**拒绝存档**而不是按自然日近似——否则同一 `horizon_days` 在不同判断里代表不同长度，M3 的分组统计失去可比性；
11. **每条验证规则必须有稳定标识**：`rule_id` 在单份判断内唯一（缺省按数组下标生成 `R{n}`），M3 用它定位规则状态，禁止依赖数组顺序；`on_hit` 目前只允许 `to_verify`（M3 再扩展 `hit`/`miss`/`review`）；
12. **可计算性硬校验**：`price_touch`/`price_break` 的 `params.level` 必须与 `key_levels` 对应字段中的某个价位一致（±0.5%），`stop_loss` 只允许 `price_break` 且以收盘价确认；`logic_invalid` 至少提供 `watch_tags` 或 `event_types`；
13. **方向与论证不得自相矛盾**：`direction.type` 为 bullish/bearish/neutral/conditional 时，`thesis.current_side` 必须分别为 bull/bear/neutral/neutral；正常判断必须同时给出 `bull_core` 与 `bear_core`；
14. **收益口径在存档时冻结**：`evaluation` 块记录入场规则（`T_CLOSE`）、个股起点价与复权因子、基准起点点位、最小超额阈值；方向验证一律以「个股复权收益 − 基准收益」判定，禁止事后用别的起点回算。`neutral_scored=false` 与 `degraded_scored=false` 表示这两类样本不进入胜率分母（重复计入口径见 §9.2）；
15. **事实按运行隔离**：`unit_fact` 以 `run_id + unit_id + unit_version + ts_code + trade_date` 为幂等键，重算产生新行而不是覆盖旧行；`judgment_unit_ref.fact_id` 指向本次判断实际消费的事实行，保证「三个月后回看这条判断的依据」仍然可读。

## 4. M1 能力单元清单

围绕流水线1（标的发现与深度筛选）反推，首批 11 个单元。执行顺序即流水线阶段顺序。

配套机制（非独立单元）：
- `emit_structured_judgment`：L3 判断块校验器 + 存档器；
- `data_quality_gate`：统一数据质量校验入口（总纲 5.5），所有单元取数前经过。

**明确推迟到 M2+**：异动检测、事件解读、北向资金（数据已断供，见第 10 章）、持仓决策、验证归因类单元。

**M1 内部落地顺序（最小闭环优先）**：
1. tushare-ingest + `data_quality_gate`（数据地基）；
2. `calc_valuation_percentile` + `emit_structured_judgment`（跑通「compute 单元 → L3 校验 → 判断存档」最小闭环）；
3. 流水线引擎串通 S0→S5 骨架（先以 2~3 个单元跑通全流程，产物可达最小验收）；
4. 横向铺开其余单元与前端页面。

原则：先保证「一条数据从落库到判断存档」的端到端链路真实可用，再扩充单元数量，避免骨架未通先堆单元。

## 5. 完整 Spec 样例 A：估值分位（pair 型）

### 5.1 单元定义
- **unit_id**：`calc_valuation_percentile`（compute）+ `interpret_valuation`（interpret），配对使用
- **类别**：基本面分析类
- **所属流水线**：P1 阶段一（初筛信号）与阶段三（全链路分析），两阶段复用同一事实表

### 5.2 方法论来源
- 参考 skill：`valuation_snapshot_skill`（提炼 Step 1 口径选择、Step 4 预期解读、全部 5 条质量要求）
- 流派：成长+趋势（本单元对流派不敏感，属通用层）

### 5.3 输入数据契约（calc_valuation_percentile）

| 项 | 值 |
|---|---|
| 来源表 | `daily_basic`（手册接口卡：180 次/分钟，幂等键 `(trade_date, ts_code)`） |
| 使用字段 | `close, pe, pe_ttm, pb, ps_ttm, dv_ttm, total_mv, circ_mv` |
| 历史窗 | 近 3 年（约 750 个交易日），不足 2 年则降级为「仅当前值，无分位」 |
| 更新时机 | 每日盘后流水线取当日全市场 1 页（`trade_date` 参数，limit=10000） |
| 口径约束 | 分位计算统一用 `pe_ttm`（不用静态 `pe`）；`pe_ttm<=0` 的样本**不剔除**，单独计入「亏损样本」，分位按盈利样本计算并标注亏损样本占比 |
| 缺失处理 | 当日 `daily_basic` 缺行 → 标记 `data_status=missing`，禁止沿用昨日值 |

### 5.4 计算规范（calc_valuation_percentile）

输出事实表 Schema（`valuation_fact.json`）：

```json
{
  "ts_code": "000001.SZ",
  "trade_date": "20261122",
  "data_status": "ok",
  "current": {"pe_ttm": 5.2, "pb": 0.58, "ps_ttm": 1.1, "dv_ttm": 4.8, "total_mv_yi": 3120.0},
  "percentile_3y": {"pe_ttm": 18.5, "pb": 22.1, "ps_ttm": 35.0, "method": "empirical_cdf"},
  "band_3y": {"pe_ttm": {"p10": 4.1, "p25": 4.8, "p50": 5.6, "p75": 6.9, "p90": 8.2}},
  "loss_ratio_3y": 0.02,
  "relative_industry": {"industry_code": "801780", "pe_ttm_median": 6.1, "vs_industry": -0.15},
  "notes": ["分位基于盈利样本（98%）计算", "行业中位数取申万一级当期"]
}
```

计算规则：
1. 分位用经验 CDF（`当前值在3年序列中的排名%`），不用正态假设；
2. `relative_industry.vs_industry = (个股pe_ttm / 行业中位数) - 1`；
3. 阈值分档（供下游引用，不在本单元做判断）：`p25 以下=低位，p25~p75=中位，p75 以上=高位`；
4. 单测要求：正常序列、不足2年、全亏损样本、当日缺行四个用例。

### 5.5 解读规范（interpret_valuation）

**输入**：`valuation_fact.json` + 单元5.2 的方法论指令。
**LLM 核心指令**（提炼自 valuation_snapshot_skill，改写为无人值守可执行版）：

```
你基于已计算的估值事实表做解读，禁止自行计算或引入事实表以外的数字。
按以下顺序输出：
1. 口径适配判断：结合 interpret_business_overview 输出的业务特征，
   判断当前最适用的估值口径（盈利驱动看PE、高增长未稳定看PS、
   资产属性看PB、周期属性结合景气位置），并说明理由。
2. 位置判断：历史分位 + 同业相对位置 → 明显偏低/偏低/合理/偏高/明显偏高。
   若亏损样本占比>10% 或分位窗口不足，必须降级结论并说明。
3. 预期解读：当前价格隐含了什么增长/盈利假设；哪些变量一旦失手估值最易被压缩。
4. 重估触发：列出未来最可能改变估值水平的事件（关联 verification watch）。
禁止事项：不得给出"买入/卖出"字样；不得脱离事实表数字抒情；
历史分位必须讲清口径与窗口边界。
```

**输出**：报告段（markdown，模板对齐 skill「估值快照」的六节结构）+ 判断块（按 3.1 Schema，`dimension="valuation"`，`facts_used` 必须逐条引用事实表指标名）。报告中所有关键数字必须使用溯源标记 `[[metric|value]]` 包裹（前端 TraceTooltip 渲染契约，见《前端设计详案》第 7 节），标记内指标名必须与 `facts_used` 一致。L3 校验链含机械的「正文数字扫描」：报告 markdown 中所有未被 `[[...]]` 标记包裹的数值 token 一律判校验失败并回喂重试，封死叙述文本绕过 `facts_used` 校验编造数字的旁路。

### 5.6 质量要求
1. 先选对口径，再谈高低（skill 原文保留）；
2. 结论必须回到经营与预期，不停留在数字表层（skill 原文）；
3. 本项目补充：所有数字必须能在 `facts_used` 中溯源，校验器逐条比对；
4. 本项目补充：结论五档为枚举，禁止输出枚举外表述。

### 5.7 失效与降级
- 事实表 `data_status != ok` → interpret 仍执行，但报告标注「数据异常」，结论强制 `data_gaps` 标注，confidence 最高「低」；
- 亏损样本占比 > 30% → pe_ttm 分位标注「不适用」，解读改以 ps_ttm / pb 为主口径；
- L2 输出 Schema 校验失败 → 重试 2 次 → 仍失败则降级存档（仅事实表，无解读），流水线继续，日志告警。

### 5.8 测试要求
- compute：4 个单测用例（见 5.4）；
- interpret：维护 10~15 个「黄金样本」（人工确认过的历史输出；5 个样本在 LLM 输出非确定性下统计意义不足），每次 prompt 或模型版本变更后回放比对；**另设周期性自动回放（每周固定日 + 每次发版前全量回放）**——模型供应商会静默升级同名模型权重，此类漂移不触发「变更」事件，只能靠周期回放捕获。**回放执行方式**：每个样本每次回放执行 2 次、结论档位取众数，降低供应商非确定性导致的误判。**回归判定标准**：漂移 1 档以内的样本占比 ≥80% 为通过（10~15 个样本下至多允许 2~3 个漂移 1 档）；任一样本漂移 ≥2 档、或 `facts_used` 出现事实表外指标、或 `logic_tags` 越界，即判回归失败，禁止上线。

## 6. 完整 Spec 样例 B：多空逻辑对撞（interpret 型）

### 6.1 单元定义
- **unit_id**：`interpret_bull_bear_collision`
- **类别**：决策辅助类；**所属流水线**：P1 阶段三（全链路分析的最后解读环节），是主判断的直接生产者

### 6.2 方法论来源
- 参考 skill：`bull_bear_case_builder_skill`（完整提炼 6 个 Step 与全部 5 条质量要求，这是插件中质量最高的 skill 之一）
- 流派：通用层（防确认偏误机制）

### 6.3 输入数据契约
本单元不直接取数，输入为上游事实表打包：

```json
{
  "stock_code": "000001.SZ",
  "trade_date": "20261122",
  "business_overview": {"main_business": "...", "revenue_structure_top3": [...]},
  "fundamental_quality": {"revenue_yoy": 8.2, "dt_netprofit_yoy": 15.1, "roe": 11.3,
                          "grossprofit_margin_trend": "stable", "redflag_items": []},
  "valuation_fact": {"pe_ttm_pct": 18.5, "pb_pct": 22.1, "vs_industry": -0.15},
  "trend_fact": {"above_ma200": true, "rs_vs_hs300_60d": 0.86, "dist_52w_high_pct": -0.12},
  "key_levels_fact": {"support": [10.85], "resistance": [12.40], "atr_stop_2x": 10.40,
                       "calc_basis": "20日高低点+2倍ATR（不复权）"},
  "event_facts": {"forecast_pending": true, "share_float_30d": null}
}
```

任一上游事实缺失时填 `null` 并在 `data_gaps` 记录，禁止 LLM 补充猜测值。

### 6.4 解读规范（LLM 核心指令）

```
围绕"未来 {horizon_days} 天该股是否有超额收益机会"这一命题，
同时构建最强版看多与看空论证，输出对照判断与结构化主判断。

Step1 双方共用事实底座：只允许引用输入事实表中的数据，
      任何一方不得使用对方未引用的独家"事实"。
Step2 看多论证：市场可能低估了什么→哪个变量正在改善→为何有持续性→
      验证后弹性来自哪里。禁止"行业空间大""公司优秀"类空话。
Step3 看空论证：市场可能高估了什么→哪些改善是阶段性噪音→哪些约束阻碍兑现。
      看空必须是最强版本，禁止机械挑刺。
Step4 对照判断：证据直接性/可验证性/时间敏感度/赔率影响四维对照，
      得出当前占优方向（看多/看空/暂不站队）与置信度。
Step5 输出验证点：接下来最需要跟踪的验证条件，转化为 verification_rules。

质量要求（全部硬性）：
1. 多空共用同一事实底座，校验器会比对两侧引用的指标；
2. 结论必须落到具体变量与验证条件，不确定就写"暂不站队"+等待条件；
3. 某一方证据明显薄弱时直接指出，不做表面平衡；
4. 禁止输出"建议买入/卖出"，仅输出方向占优判断；
5. 所有数字仅可来自输入事实表，缺失即标注。
```

**输出**：报告段（模板对齐 skill「多空论证」七节结构）+ **主判断块**（按 3.2 Schema 完整输出，本单元是主判断的唯一生产者）。

### 6.5 本单元特有的 L3 校验规则
1. `thesis.current_side != "暂不站队"` 时，`verification_rules` 至少 2 条；`= "暂不站队"` 时至少 1 条 `logic_invalid`（等待条件型）；
2. `key_levels.stop_loss` 必须存在且低于当前价（bullish 时）；bearish 反之；neutral 可为空。**边界豁免**：当 `calc_key_levels` 事实表中不存在满足条件的止损位时（如现价已跌破 ATR 止损——成长+趋势流派「缩量回踩支撑」类入选标的的常见形态），允许 `stop_loss=null` 并在 `data_gaps` 标注「现价已低于计算止损位，判断需重估」，禁止因无合法价位机械降级；
3. `logic_tags` ⊆ 受控词表，越界标签触发重试；
4. **价位可计算化铁律**：`key_levels` 的支撑/压力/止损数值必须逐一引用 `calc_key_levels` 事实表数值（校验器硬比对，偏差超过 ±0.5% 即判失败回喂重试）——LLM 只负责「在计算出的价位中做主次选择与叙事」，禁止给出事实表以外的价位数字。

### 6.6 失效与降级
上游事实表中 ≥2 个缺失 → 判断 confidence 强制「低」，`data_gaps` 完整列出；direction 只允许 `neutral` 或 `conditional`。L2 校验重试耗尽仍失败时按 7.3 降级矩阵生成机械降级判断。

## 7. 流水线1 编排设计（M1 主场景）

### 7.1 阶段流程

```
触发：每个交易日 17:30（Tushare 日线数据落库完成后）
  │
  ▼
[S0 数据质量门] data_quality_gate
  检查当日 daily / daily_basic / fina 类表落库完整性与时效
  不达标 → 自动延迟重试（每30分钟重查，数据源晚披露属常态）
           至 22:00 仍不达标 → 整线挂起告警，禁止降级静默运行（总纲 5.5）
  │
  ▼
[S1 全市场量化初筛]  unit 1→2→3→4→11（批量 compute 单元，单元级并行）
  screen_universe_baseline   全市场 ~5000 → 流动性/市值/停牌/ST 过滤 → ~800
  calc_trend_strength        批量计算趋势强度事实（整池一次执行）
  calc_growth_screen         批量计算成长性事实
  calc_valuation_percentile  批量计算估值分位事实
  calc_key_levels            批量计算支撑/压力/ATR止损事实（不复权口径）
  （5 个单元均为 BATCH 粒度：各执行一次整池计算，产出批量落 unit_fact，事实在 S3 入口装配为 per-stock FactBundle）
  │
  ▼
[S2 硬伤剔除] unit 5（compute，规则化，可解释）
  screen_financial_redflag   高质押/近期大额解禁/审计非标/连续亏损/股东户数激增
  → 重点分析池 ~30-50 只
  │
  ▼
[S3 全链路分析] unit 6→7→8（每只标的串行取数、可并行执行）
  interpret_business_overview       业务速览（含主业构成变化）
  interpret_fundamental_quality     财务质量解读
  interpret_valuation               估值解读（消费 S1 估值事实表）
  │
  ▼
[S4 综合结论] unit 9 + L3（每标的并行执行，LLM 并发限流=4，与架构文档 4.3 对齐；禁止串行——strong 档 30~50 只串行会击穿 2h 总时长上限）
  interpret_bull_bear_collision     消费全部事实表 → 报告 + 主判断
  emit_structured_judgment          校验、冻结、存档
  │
  ▼
[S5 综合排序] unit 10
  calc_composite_rank   可解释加权评分（因子权重配置化并纳入方法版本）
  │
  ▼
产物：① 每日候选池 TopN（默认 10） ② 重点池每只标的全链路报告
      ③ 对应主判断记录（供流水线3 巡检）
```

### 7.2 综合评分设计（unit 10 要点）

- 因子全部来自既有事实表（趋势强度分位、成长分位、估值分位、财务红旗计数），做横截面 0-1 标准化后加权；
- 权重配置文件纳入方法版本管理，调整权重 = 方法版本变更（总纲 5.2 / 5.4）；
- 评分必须可解释：输出每只标的的「因子得分明细」，禁止黑盒总分；
- 阶段一用同一套评分做初筛排序（阈值宽松），阶段五对重点池精排，保证全链路口径一致。注意：初筛排序引用**同一权重配置文件**的因子子集（趋势/成长/估值，此时红旗计数因子尚不存在），由 `screen_universe_baseline` 执行；`calc_composite_rank` 只在 S5 做全因子精排——两者共享权重配置，避免口径漂移。

### 7.3 降级矩阵

| 异常 | 行为 |
|---|---|
| S0 数据门不达标 | 自动延迟重试（30分钟间隔，至 22:00）；仍不达标 → 整线挂起并告警（webhook 通道见架构文档 6.2），人工介入 |
| 某只标的 interpret Schema 校验失败 | 该标的降级为「仅事实表存档」+ **生成机械降级判断**（由框架按 3.2 Schema 骨架生成、非 LLM 产出：direction=neutral、confidence=低、`degraded=true`、有效期默认 5 个交易日、`verification_rules` 仅含一条到期重估 `direction_fail` 规则、`data_gaps` 注明降级原因，不含 LLM 叙事），保证标的仍进入流水线3 验证链路；emitJudgment 对正常/降级结果单路径消费；M3 效果统计默认过滤 `degraded=true` 样本，其余标的继续 |
| fina_indicator 限流/漏数 | 财务维度标记 `data_gaps`，红旗检查降级为「部分覆盖」并在报告标注 |
| 全市场接口 40203 | 按《Tushare 手册》3.1 限流规则阻塞等待，禁止跳过 |

2. **可计算化**（把「判断收缩是否健康」翻译为指标公式+阈值）；
3. **结构化判断输出**（第 3 章 Schema + 校验器 + 受控词表）。

## 9. 版本管理与归因对接规范

### 9.1 版本对象与规则

| 版本对象 | 版本载体 | 变更即升版 |
|---|---|---|
| 能力单元 spec | `units/<unit_id>/SPEC.md` front-matter `version` | 计算公式、阈值、prompt 指令、输出 Schema 任一变更 |
| 方法版本（method_version） | 配置文件（单元版本清单+评分权重+受控词表快照） | 任一下属单元升版或权重调整 |
| 受控词表（logic_tags） | 随方法版本快照冻结 | 新增标签须评估对归因统计连续性的影响 |

规则：
- 主判断记录的 `method_version` 是其效果的统计分组键——**禁止在旧判断存续期内修改其关联版本**；
- 每次升版附带一行变更说明（改了什么、为什么），这是总纲 5.4「人工主导迭代」的最小记录单位。

### 9.2 与流水线3 归因的对接点

总纲 5.3 归因流程（定量拆解 → 排查外因 → 定位内因）在数据侧的对接：

| 归因步骤 | 依赖字段 |
|---|---|
| 定量拆解（市场/行业/个股贡献） | 主判断 `direction.horizon_days` + index_daily（基准）+ sw 行业指数 |
| 排查外因（公告/事件/政策/资金） | `verification_rules[type=logic_invalid].watch_tags` + 事件表（M2 建设后） |
| 定位内因（方法缺陷） | `method.units_used` → 定位到具体单元 → 按单元维度统计胜率/偏差分布 |

效果统计的三个最小口径（M3 实现）：按 `logic_tag` 分组的命中率、按单元版本分组的方向正确率、按偏差类型（四类验证规则）的分布。

**统计去重口径（防样本自相关，M3 实现前必须锁定）**：同一标的在方向存续期内每日产出新主判断，直接统计会因样本高度重叠而虚增样本量、虚高胜率置信度。约定：同标的存在未过期的前序主判断且方向未变时，新判断 `direction.is_reaffirm=true`（重申判断）；M3 效果统计默认仅取各「判断实例」的首判断（`is_reaffirm=false`）作为样本，重申判断只用于前端历史轨迹展示，不进入胜率分母。
