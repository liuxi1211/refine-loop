| # | 偏差 | 理由 | 登记位置 |
|---|---|---|---|
| D1 | 估值事实数值写成 `{value, unit}` 指标叶子，而非详案 5.4 示例的裸数字 | L3 的 `FactMetrics`/`FactsUsageValidator` 只认叶子；裸数字无法做「名+值+单位」三重比对 | SPEC ⑦ + 本文 |
| D2 | 估值事实新增 `window{start_trade_date,end_trade_date,sample_days}` | 详案 5.5 要求「窗口不足必须降级」，窗口边界必须是可引用事实 | SPEC ⑦ |

| D4 | 降级判断也需要 `report_id`：写一条 `status=DEGRADED`、`file_path=NULL` 的 `report` 占位行 | `judgment.report_id NOT NULL` 与「降级仅事实存档」冲撞；真实报告归档属 T18 | 《技术架构》§4.4 落地说明 + 本文 |

| D6 | `judgment.expire_at` 实体用 `String`（ISO 文本） | 该列是 T2 登记的 `DATE` 类型例外（附录 E6），避免新增 `LocalDate` 类型处理器 | `JudgmentEntity` javadoc |

### 4.1 T12 前复查改造（2026-11-26）

> 完整背景见 `docs/T12前设计复查与改造记录.md`。这里只登记**与本文档既有结论不同的部分**（口径变更，非新增能力）。

| # | 变更 | 原口径 | 现口径 | 理由 |
|---|---|---|---|---|
| D10 | `horizon_days` 单位 | 存档器按自然日 `plusDays` 推算 `expire_at`；降级路径按 5 交易日、日历缺失时退 7 自然日 | 一律按**交易日**（`trade_cal`）计算；判断块自报 `expire_at` 必须与服务端计算相等；日历不足拒绝存档 | 同一字段两套单位会让效果统计的分组不可比，且历史数据无法追溯修正 |
| D11 | 主判断 payload 版本 | 无版本字段 | `schema_version="2.0"`，新增 `run_id`、`evaluation`、`benchmark` 三字段、规则 `rule_id`/`expected`/`price_field`/`from` | 判断要能被 M3 计算，需要「起点 + 基准 + 阈值 + 规则身份」四要素 |
| D12 | 可验证性门槛 | 有方向即存档 | 取不到当日个股 `close/adj_factor` 或基准 `index_daily.close` 时**拒绝存档** | 「有方向但没有起算点」的判断永远无法判对错，存档只会制造噪声 |
| D13 | `unit_fact` 幂等键 | `(unit_id, unit_version, ts_code, trade_date)`，upsert 覆盖 | `(run_id, unit_id, unit_version, ts_code, trade_date)`，**只追加不覆盖**；同 run 内容变化即拒绝 | 覆盖会让冻结判断的溯源在第一次重跑时断链 |
| D14 | `unit_fact` 读回完整性 | `schemaVersion` 用 `unitVersion` 冒充、`notes` 固定为空 | 新增 `schema_version`/`notes` 列并真实回读 | 降级原因（当日缺行、行业缺失）落库后必须能被 S3 装配读到 |
| D15 | 归档编号范围 | `judgment` 无 `run_id`；`judgment_unit_ref` 只有单元版本 | 增 `run_id`；`judgment_unit_ref` 增 `fact_id`，compute 单元找不到本次事实行即拒绝 | 把「判断 → 事实 → 原始表」链条钉死 |
| D16 | 存档并发策略 | 「唯一索引兜底 + 冲突重试 ≤3」 | 进程内串行（`synchronized`）+ 唯一索引兜底，冲突重试保留 | SQLite DEFERRED 事务先读后写在 WAL 下可能直接 `BUSY_SNAPSHOT`（消息不含 UNIQUE，不触发原重试分支）；存档事务只含本地短写，串行更确定 |
| D17 | 行业归属查询 | 只按 `out_date` 过滤 | 增加 `in_date <= trade_date` | 否则历史回放会把「未来才纳入」的成分算进当日同业基线（前视偏差） |
| D18 | 质量门非交易日判定 | 无日历且无行情 → `EMPTY` | 日历缺失/非法 → `FAIL`（新增 `L0_TRADE_CALENDAR` 项）；仅 `is_open='0'` 才 `EMPTY` | 空库不能被推断为「休市」，否则流水线会静默跑空 |
| D19 | 接入作业失败语义 | 单股部分失败仍可 SUCCESS；上游空结果跳过；整块删插缺键静默丢行 | 任一单股失败即整表 FAILED；上游空结果显式删旧块；缺键抛错 | 「部分成功」会让质量门与用户同时对数据完整性产生错误信心 |
| D20 | 作业恢复 | 重启后 RUNNING 永久悬挂 | 启动 `IngestRecoveryRunner` 置 FAILED；编排恢复见 PENDING/RUNNING 即判 FAILED | 不恢复则既不能重试，也让 S0 永久失败 |
| D21 | LLM 重试与记账 | Spring AI 默认重试模板（最多 10 次）叠加外层 120s 超时；记账在重试 try 内 | 显式传空 `RetryTemplate`，重试只由 `LlmInvoker` 控制；记账移出重试路径 | 内层退避会先吃满超时变成「超时不可重试」；记账失败会导致重复付费 |
| D22 | 报告数字校验容忍度 | 掩码不含证券代码/市场术语；数值仅 0.1% 相对误差 | 掩码补 `000001.SZ`/`801780.SI`/`2025Q3`/`MA20`/`近3年` 等；数值增加「按书写精度最后一位四舍五入」 | 否则真实 A 股报告几乎必然被判「裸数字」或「篡改」，三次重试后全量降级 |
| D23 | 单元注册校验 | 只校验 scope/modelProfile | 增加「注解 type 必须与实现接口一致」（COMPUTE⇒ComputeUnit、INTERPRET⇒InterpretUnit） | 错配要到流水线执行期才暴露为 CCE，注册期就该拒绝 |

```sql
-- 0) 先取本次运行编号（日志里的 runId，或取当日最新一条）
SELECT run_id, COUNT(*) AS rows FROM unit_fact
 WHERE unit_id='calc_valuation_percentile' AND trade_date='20261125'
 GROUP BY run_id ORDER BY MAX(id) DESC;

-- ① 输出行数 == 在市数（把 <RUN_ID> 换成上一步取到的值）
SELECT (SELECT COUNT(*) FROM unit_fact WHERE run_id='<RUN_ID>'
          AND unit_id='calc_valuation_percentile' AND trade_date='20261125') AS facts,
       (SELECT COUNT(*) FROM stock_basic WHERE list_status='L') AS listed;

-- ② 抽查：分位与手工计算可复核（payload 里含 window.sample_days 与 band_3y）
SELECT ts_code, data_status, schema_version, notes, payload FROM unit_fact
```

### 5.3 人工确认要点（T11 检查点）

1. 判读「同一 run 内 `unit_fact` 行数 == `stock_basic` 在市数」，且抽查的 5 只分位与手工计算一致；
2. 报告正文里每个数字都能在溯源弹层（`judgment_unit_ref.output_summary.facts_used` → `unit_fact`）对上，且 `judgment_unit_ref.fact_id` 能回查到同一行；
3. 人为构造降级（把某只标的 `daily_basic` 当日行删掉）后重跑，确认**该标的被拒绝生成方向判断**（缺行情起点 → 6001）或降级判断落库且 `data_gaps` 说明原因——注意：复查后缺行情起点属「拒绝存档」，不再是静默降级；
4. 确认 `llm_usage` / `ingest_log` / `rate_limit_counter` 三表均有真实数据；
5. 重跑同一天后，用 `fact_id` 回查旧判断的事实行，确认其 `payload` 与首次一致（验证「事实按 run 隔离」真的生效）；
