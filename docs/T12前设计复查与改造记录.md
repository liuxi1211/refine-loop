# T12 前设计复查与改造记录

> 触发：T10 完成、整体进度过半时，暂停推进 T11 联调与 T12 流水线，重新审视「项目定位 → 用户闭环 → 模块设计 → 前后端实现」。
> 方法：以「一个不做专业分析的 A 股个人投资者，盘后/周末打开系统」为唯一评判视角，不看既有设计的自我论证，只看链路能不能跑通、判断能不能被验证、越晚改是否越贵。
> 结论：**定位与分层方向可以保留；但判断/事实契约必须在 T12 之前改**，否则流水线一落地就会把不可验证的结构固化进历史数据。

---

## 1. 一句话定位与真正的闭环

**定位**：给非专业个人投资者的「盘后判断记分本」——每晚对关注/持有的票给出一条**事先写死判定条件**的判断，到期自动打分，诚实累积战绩，再由人决定要不要改方法。

**最小闭环**（本次复查的验收视角）：

```
数据就绪（S0）→ 有候选/有关注标的 → 一条可验证判断
    → 到期自动判定（命中/落空/失效）
    → 周末看战绩与典型错例 → 人工调方法 → 版本冻结回流放比对
```

对照这条链路，原设计的断点不是「能力单元不够多」，而是三处**结构性缺口**：

| # | 缺口 | 后果（用户视角） | 越晚越贵的理由 |
|---|---|---|---|
| 1 | 判断没有「结果」定义 | 判断只被存档、永远不会被判对错；半年后仍无法回答「这系统准不准」 | 判断一经存档即冻结，补字段只能靠推测回填 |
| 2 | 有效期单位双轨（自然日 vs 交易日） | 同一 `horizon_days=60` 在不同判断里长度不同，胜率分组无可比性 | 每条历史判断都带这个字段，无法追溯修正 |
| 3 | 事实按「单元+标的+日期」覆盖 | 次日重跑后，旧判断「当时依据什么」被静默改写，溯源链断在第一次重跑 | 一旦有真实历史，覆盖已发生，证据不可再生 |

## 2. 复查发现的问题（按严重度）

### P0-1 判断结果不可计算

- 证据：`docs/核心能力体系设计详案.md` 原 §3.2 的 `verification_rules` 只有 `rule_type/target/params/on_hit`，四类规则全部 `on_hit: to_verify`；`direction_fail.params` 只有一个 `expire_at`，没有基准与阈值；`target_note` 里的「相对沪深300 超额收益」只是自由文本。
- 失败场景：到期时无法回答「这只票跑赢基准算命中还是落空」；`price_touch` 没写清用 high 还是 close、从哪天开始算；规则是数组匿名元素，M3 只能靠下标定位状态，prompt 调整导致顺序变化即状态错位。
- 本次改造：
  - 每条规则增加稳定 `rule_id`（缺省 `R{n}`，单份判断内唯一）；
  - `price_touch`/`price_break` 固化 `price_field`（support→low、resistance→high、stop_loss→close）与 `from=next_trading_day`；
  - `direction_fail` 固化 `expire_at` + `benchmark=index` + `min_excess_pct`；
  - 存档时校验 `params.level` 必须与 `key_levels` 对应价位一致（±0.5%），`stop_loss` 只允许 `price_break`；
  - 新增 `evaluation` 块（入场规则、个股起点价与复权因子、基准起点点位、最小超额阈值、是否计入分母）。
- 测试：`JudgmentPayloadAssemblerTest`（规则形状/一致性）、`JudgmentArchiveServiceTest`（落库完整性）。

### P0-2 有效期口径三处打架

- 证据：原 `JudgmentPayloadAssembler` 按**自然日** `plusDays` 推算到期日；`InterpretResult` 的降级判断按**5 个交易日**；`judgment.expire_at` 列注释与 `AssembledJudgment` 注释写「交易日」；交易日历不足时降级路径还会退回 7 个自然日。
- 失败场景：同一 `horizon_days` 在正常/降级/不同日期三处代表不同长度；跨长假时到期日落在哪一天不确定；M3 按 horizon 分组统计失真。
- 本次改造：
  - 新增 `JudgmentExpiryRule` 端口 + `JudgmentExpiryCalculator`（读本地 `trade_cal`），判断域**不再依赖 capability**；
  - `expire_at` 一律由日历计算，判断块自报值只允许与服务端计算结果**完全相等**，否则 6001；
  - 日历不足时**拒绝存档并提示补数**，删除「自然日近似」这条降级路径（`AbstractInterpretUnit` 同步收紧）；
  - payload 增加 `horizon_unit: "trading_days"` 显式声明。
- 测试：`JudgmentExpiryCalculatorTest`（跨周末/节假日、日历不足拒绝）、`AbstractInterpretUnitTest`（日历不可用即抛错）。

### P0-3 事实按「单元+标的+日期」覆盖，判断溯源会断

- 证据：原 `unit_fact` 唯一键 `(unit_id, unit_version, ts_code, trade_date)` 且 upsert `DO UPDATE`；`judgment_unit_ref` 只记 `unit_id/unit_version`，不指向具体事实行；`judgment` 无 `run_id`。
- 失败场景：今天判断引用的事实，明天重跑同一单元即被覆盖；三个月后打开历史判断，看到的「依据」其实是后来的数据。
- 本次改造：
  - `unit_fact` 幂等键改为 `(run_id, unit_id, unit_version, ts_code, trade_date)`，**只追加不覆盖**；同 run 重复提交相同事实为 no-op，内容变化直接拒绝；
  - 新增 `schema_version`、`notes` 列（此前 notes 落库后再读不回来，降级原因在 S3 装配时丢失）；
  - `judgment` 增加 `run_id`，`judgment_unit_ref` 增加 `fact_id`（compute 单元必须能找到本次运行的事实行，找不到即拒绝存档）；
  - `FactStore` 读写全部带 `runId`，保存改为单事务批量。
- 测试：`FactStoreTest`（同 run 幂等 / 跨 run 不覆盖 / 缺 runId 拒绝）、`T11ClosureChainIntegrationTest`（溯源按 run 校验）。

### P1-1 行业归属存在前视偏差

- 证据：`SwIndustryMemberMapper` 只按 `out_date` 过滤，未限制 `in_date <= trade_date`。
- 失败场景：回看半年前某日时，把「下个月才纳入」的行业归属算进了当日同业基线，历史分位与相对行业位置都被未来信息污染。
- 改造：两个查询都加 `in_date <= tradeDate`；新增回归用例断言「未来才生效的成分不进入当日基线，且单标的行业码为空」。

### P1-2 数据质量门会把「空库」判成「非交易日」

- 证据：原判定 `"0".equals(isOpen) || (isOpen == null && dailyCount == 0)`。
- 失败场景：首次部署、`trade_cal` 未回填时，S0 返回 `EMPTY`（不算失败），流水线静默跑空；用户以为「今天休市」。
- 改造：`isOpen` 缺失或非法直接 `FAIL` 并新增 `L0_TRADE_CALENDAR` 检查项，提示先回填 `trade_cal`；只有明确的 `is_open=0` 才是 `EMPTY`。

### P1-3 接入作业会「伪装成功」

- 证据：`IngestJobService.afterPerStock` 在「已有部分数据」时不抛错；整块删插/按月回补在上游返回空时直接跳过；`IngestOrchestrator.restoreFromDb` 只看 FAILED 判定整次编排结果；单表作业没有在飞集合；进程重启后 RUNNING 行永久悬挂。
- 失败场景：1000 只股票里 300 只失败仍标 SUCCESS；上游更正后撤回的数据永远删不掉；重启后作业卡在 RUNNING，既不能重试也让 S0 一直失败。
- 改造：
  - 任一单股失败即整表 `FAILED`；
  - 按日/按月/按公告整块回补遇空结果时**显式删除旧块**（新增 `deleteBlock`/`deleteByDateRange`）；
  - 整块删插遇缺失幂等键改为抛错（原为静默丢行）；
  - 编排恢复时存在 PENDING/RUNNING 即判 `FAILED`；
  - 新增 `IngestRecoveryRunner`：启动时把遗留 RUNNING/PENDING 置 FAILED；
  - 单表作业增加在飞集合：重复提交 409，且与每日编排互斥（双向检查）。

### P1-4 LLM 调用层有两处会放大成本或误判

- 证据：`OpenAiChatModel`/`AnthropicChatModel` 未传 `retryTemplate`，Spring AI 默认模板自带最多 10 次重试，叠加外层 120s 硬超时；`LlmInvoker` 把用量记账放在重试 try 内，记账失败会被当成调用失败再调一次模型。
- 失败场景：一次 5xx 在内部退避中吃满超时，被判「超时（不重试）」；SQLite 忙导致记账失败时用户被重复计费。
- 改造：两处 builder 显式传空 `RetryTemplate`（重试只由 `LlmInvoker` 控制）；记账移出重试路径，失败只记 error 日志并保留已成功的模型结果。

### P1-5 校验链会误杀合法报告

- 证据：`ReportNumberScanner` 的掩码不含证券/指数代码、`2025Q3`、`MA20`、`近3年` 等 A 股报告高频标识；`FactsUsageValidator` 只允许 0.1% 相对误差，事实 18.5432 写成 18.5 会被判「篡改」。
- 失败场景：真实估值报告几乎必然出现 `000001.SZ`、`沪深300`，导致三次重试后全量降级，白烧调用。
- 改造：掩码补充证券/指数代码与市场术语；数值比对增加「按书写精度最后一位四舍五入」容忍（18.5432→18.5 通过，→18.9 仍失败）。

### P1-6 契约测试与实现漂移

- 证据：`.claude/rules/02` 的 `judgment` 模板写 `direction VARCHAR(12)` 大写三值、`confidence DECIMAL(5,4)`、`expire_at CHAR(8)`，实际 schema 是 `VARCHAR(16)` 小写四值、`VARCHAR(4)` 中文、`DATE`。
- 改造：模板按实际 schema 修正，并把「事实/证据表按运行隔离」写成通用条款（02 §4 第 6 条）。

### P2 已记录但本轮不改（附退出条件）

| 项 | 现状 | 退出条件 |
|---|---|---|
| `is_reaffirm` 判定口径 | 只按「更早交易日 + 未过期 + 同方向」，未排除 neutral/降级/跨 pipeline | M3 效果统计落地前，改为按「判断生命周期状态」而非 `expire_at` 判定 |
| 除权后价位规则一律失效 | 详案原表述为「遇除权即置失效」 | 已改为「按 `adj_factor` 比例调整后继续验证，比例偏差 >3% 才失效」，巡检实现时落实 |
| 报告文件路径不含 run/seq | `reports/{date}/{code}.md` 同日重跑会覆盖正文 | T18 报告模块落地时改为 `{date}/{code}/{seq}.md` |
| 右侧「今日一句话」等报告生成类调用 | 尚未实现 | T18，走 `ReportGenerator` 轻量模板 |
| 有效性检查 `unit_fact` 体量 | 按 run 追加后行数 = 运行次数 × 事实数 | 流水线落地时按 run 归档策略清理（保留 REPORT_POOL 永久、其余 90 天） |

## 3. 前后端与运维链路的改造

### 3.1 首启链路（此前走不通）

原链路：空库 → 首屏主按钮是「一键每日增量」 → 41 表全部 SUCCESS → 健康度全绿 → 用户以为数据就绪，实际只有几天历史；回填向导只能「生成计划」，无法执行，关闭即丢。

改造：
- 数据总览页识别「未初始化」（所有表既无行数也无最新日期）：隐藏每日增量，改为「开始初始回填」引导条；
- 回填向导第二步每个批次新增「执行本晚」，按后端 `plan.tables` 顺序逐表调用既有 `POST /ops/tables/{table}/backfill`（后端单线程队列保证串行），支持「执行全部未完成批次」；
- 计划与已完成表存 `sessionStorage`，刷新后恢复；
- 删除前端硬编码的标准表清单（与后端不一致的第二个事实源），改为展示后端返回的批次。

### 3.2 失败可恢复

- 启动恢复把遗留 RUNNING 置 FAILED（`IngestRecoveryRunner`），前端「重试」因此可用；
- 编排恢复：有 PENDING/RUNNING 即判 FAILED，不再把「只跑了几张表」显示为已完成。

### 3.3 信息架构与文案

- 路由改为分区：`/data/overview`、`/data/jobs`（质量门作为 `?tab=quality`）；旧路径保留 `alias` 以免书签失效；为 M1 的 `/dashboard`、`/candidates`、`/judgments` 留出命名空间。
- 侧栏分「数据中心 / 投研工作台 / 账户」三组；未上线模块改为静态说明，不再用「点了弹 toast」的伪入口。
- 移除 Google Fonts 外链（部分网络下阻塞首屏数十秒）；环境标识改为 `import.meta.env.DEV` 驱动，去掉写死的「本地开发 · 8080」。
- 登录页不再公开默认口令；健康度阈值文案与后端规则（`lagDays > 7`）对齐，删除「≤2 个交易日」这一不存在的口径。
- 写操作按钮按 `data:ingest` 权限收起（此前 USER 点了必然 403）。

## 7. 保留的设计（不改）

这些是复查后确认「方向正确、不要为了改而改」的部分：

- **L1/L2/L3 三层执行架构**与「凡是能用代码算的，一律不进 LLM」；
- `facts_used` 的「指标名 + 数值 + 单位」硬校验与受控词表——这是与「AI 写研报」的分水岭；
- 判断冻结的编译期约束（`JudgmentMapper` 不继承 `BaseMapper` + 反射白名单）；
- 存档时固化基准、同组重跑取代不覆盖、降级与正常单路径；
- 流派锁定、S0 数据门、触发表轮询、`capability` 的 `units → runtime → spi` 单向依赖；
- BATCH 粒度的 compute 单元与「S3 入口装配 FactBundle」的划分。
