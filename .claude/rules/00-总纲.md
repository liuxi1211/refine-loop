# refine-loop 开发规范（总纲）

> 适用对象：本项目全部后端 / 前端 / 数据库 / 文档改动，包括人类开发者与 AI 辅助开发会话。
> 定位：**这是约束，不是建议**。与《技术架构与模块设计》《公共基础设施使用手册》冲突时，以本规范为准；与代码事实（`db/schema.sql`、`pom.xml`、门禁测试）冲突时，以代码事实为准并提交一次规范修正。

---

## 0. 为什么要有这组文档

项目已过「一次性能写完」的阶段：61 张表、多用户账号与权限、19 个前端组件，后续还要接能力单元、流水线、判断存档、报告、版本管理五个域。长期维护的成本不在写新代码，而在：

1. **找得到**——同一个概念只有一处实现、一个名字；
2. **改得动**——改动的影响面可预测，不靠全仓搜索；
3. **拦得住**——违反约定的代码在提交前就变成红色，而不是三个月后变成事故。

因此本规范的每条规则都尽量绑定一种**执行方式**：能交给编译器和测试的，就不写给人看。

## 1. 三级约束模型（每条规则都必须落在其中一级）

| 级别 | 含义 | 执行方式 | 违反后果 |
|---|---|---|---|
| **L1 硬门禁** | 机械可判定，构建即失败 | 编译、`mvn test`、`npm run build` 中的校验 | 无法合并 / 无法发布 |
| **L2 机器校验** | 规则已写成测试或配置 | `ArchitectureRulesTest`、`SchemaConventionTest`、`.editorconfig` | 同上（测试红） |
| **L3 人工评审** | 语义判断，无法机械判定 | Code Review 清单（见下） | 评审驳回 |

规则条目在正文中标 `[L1]` `[L2]` `[L3]`。**新增规范时必须同时回答：它由哪一级保证？** 如果只能靠"大家记得"，就不要写进规范——写进《附录：存量偏差登记》当作技术债。

一句话自检：

```bash
# 提交前自行执行（不设脚本封装，靠自觉）
mvn -B test                    # 后端编译 + 全量测试（含架构 / schema 规范校验）
cd frontend && npm run build   # 前端类型检查 + 构建（改了 frontend/ 才需要）
```

## 2. 权威顺序（冲突裁决）

1. `db/schema.sql` + `TushareTableRegistry`（表/列/幂等键的唯一事实源）；
2. `pom.xml` 依赖基准清单（《技术架构与模块设计》§1 登记）与门禁测试代码；
3. **本规范**（结构与编码约束）；
4. 设计文档（《技术架构与模块设计》《前端设计详案》《Tushare 接口对接手册》《公共基础设施使用手册》）；
5. 口头约定 / 历史代码。

「历史代码这样写的」不是理由。存量代码若违反本规范，按第 9 节处理。

## 3. 十条红线（不可协商，评审直接驳回）

| # | 红线 | 对应条款 |
|---|---|---|
| 1 | **Controller 不写业务**：不做持久化、不拼业务文案、不翻译业务语义；只解析参数、调服务、包装 `Result` | 03 §3.1、04 §2 |
| 2 | **web 层不得依赖 `data` 持久化细节**（`..data.mapper..`、`..data.entity..`）；`common` 不得依赖任何业务域 | 01 §4 |
| 3 | **生产代码禁止 `JdbcTemplate`、禁止裸 SQL 字符串**；SQL 只在 `data` 层 | 01 §5、02 §11 |
| 4 | **Controller 禁止返回 `*Entity`**；返回值必须是无持久化语义的 View/record | 04 §4 |
| 5 | **表结构只有一处事实源**：`db/schema.sql`；改 DDL 必须同一次提交内更新注册表 + 单测 + 文档 | 02 §3、§12 |
| 6 | **金额/数量/比率必须带单位口径**：列注释或列名后缀，`DECIMAL(24,4)`（金额/数量）与 `DECIMAL(20,4)`（价格/比率）不得混用 | 02 §5 |
| 7 | **时间只有两种口径**：系统时间 `LocalDateTime`（`DATETIME` 文本），业务日期 `yyyyMMdd` 的 `CHAR(8)`；禁止 `Date`/`Instant`/多套日期格式 | 02 §6、03 §7 |
| 8 | **统一响应与错误码**：所有业务接口返回 `Result<T>`，`code=0` 成功；HTTP 状态码不承载业务语义 | 04 §3 |
| 9 | **不吞异常**：`catch` 必须记日志或转换成 `ApiException`/`ErrorCode`；禁止空 `catch`、禁止 `printStackTrace`、禁止 `System.out` | 03 §8 |
| 10 | **新增依赖必须登记**：`pom.xml` 版本写进 §1 基准清单；前端新增运行时依赖需说明理由 | 01 §8 |

## 5. 新增一个东西的标准动作（照做即可）

### 5.1 新增一张业务表

1. 在 `db/schema.sql` 「业务表」段末尾追加 `CREATE TABLE`，照抄模板（`02 §4`）：`id INTEGER PRIMARY KEY AUTOINCREMENT` + 业务列 + `created_at` + `updated_at` + 唯一索引；
2. 表级注释写清：中文名 ｜ 唯一键 ｜ 单位口径；
3. 在 `data/entity/` 加 `*Entity extends BaseEntity`（新表一律继承）；
4. 在 `data/mapper/` 加 `*Mapper extends BaseMapper<*Entity>`（只放非 CRUD 查询）；
5. 单测：`SchemaSqliteTest` 表清单 + `SchemaConventionTest`（自动覆盖，无需改测试）；
6. 若表参与字典展示 → 登记 `DictEnum`（`04 §5`）；
7. 改完删本地库文件重建（1.0 前），或写迁移脚本（1.0 后，`02 §12`）。

### 5.2 新增一个域（包）

1. 顶层包一个名词（`ops`、`tushare`、`capability`…），**技术子包只在确有 3 类以上角色时才拆**（`model/dto/service/registry`）；
2. 建 `package-info.java`：写职责、允许依赖谁、不变量；
3. 在 `ArchitectureRulesTest` 的依赖矩阵里补一行（否则 L2 不生效）；
4. 对外暴露服务接口，不暴露实现；Controller 只依赖接口。

### 5.3 新增一个接口

照《公共基础设施使用手册》§14 的骨架，并满足 `04` 全部条款：路径 `/api/...`、`Result<T>`、请求 record + 校验、错误码登记、单测覆盖 400/404/409 分支。

### 5.4 新增一个公共组件（common 下）

必须先在《公共基础设施使用手册》登记（能力、位置、一行示例），否则不合并。`common` 里不得出现 `@RestController`、不得引用业务域类型。

## 6. 规范变更流程

规范不是刻在石头上的，但**改规范必须是一个可审计的提交**：

1. **提案**：在提交信息里写 `docs(rules): 提案 <条款> 由 A 改为 B`，说明触发原因（踩坑记录/新需求）；
2. **同步校验**：如果规则有 L2 校验，先改校验代码并确认它能抓到旧写法；
3. **同步代码**：把存量不合规代码一起改掉（或者新增豁免并写明退出条件）；
4. **记录**：在附录「变更历史」加一行（日期 / 条款 / 原因 / 影响文件）；
5. **不允许**：只改文档不改校验、只加豁免不写退出条件、规范与代码长期不一致。

## 7. 代码评审清单（L3，逐条打勾）

结构
- [ ] 新类是否放进了正确的包？是否新增了不该有的跨层依赖（跑 `ArchitectureRulesTest`）？
- [ ] 是否重复实现了 `common` 已有的能力（响应/错误码/分页/缓存/字典/工具类）？
- [ ] 新增文件是否超过阈值（类 400 行 / 方法 50 行 / 前端组件 300 行）？超了是否说明理由？

数据库
- [ ] 表/列/索引命名符合 `02`？金额/数量列有单位？
- [ ] 唯一键是否真的能防重？索引是否对应真实查询？
- [ ] `db/schema.sql` 与实体、注册表、测试是否同一次提交？

接口
- [ ] 路径、方法、入参校验、`Result` 包装、错误码是否合规？
- [ ] 错误文案是否是给用户看的中文，没有泄漏堆栈/内部标识？
- [ ] 是否考虑了并发/重复提交（409）与空数据？

代码
- [ ] 类与方法命名是否表达意图（不是 `handleData`/`process2`）？
- [ ] 异常是否被吞？日志级别是否正确？有没有把大对象打进日志？
- [ ] 时间、ID、随机、时区是否走了统一的 `Clock`/`Ids`/常量？
- [ ] 是否有魔法值（状态串、日期格式、阈值）应提取到枚举/常量？

测试
- [ ] 新增/修改逻辑是否有用例覆盖正常 + 异常 + 边界？
- [ ] 修 bug 是否带了回归用例？
- [ ] 是否引入了对开发库/网络/时序的依赖？

文档
- [ ] 改了公共能力是否更新《公共基础设施使用手册》？
- [ ] 改了结构/契约是否更新本规范或设计文档？
- [ ] 重大取舍是否记了 ADR（《技术架构与模块设计》§10）？

## 8. 依赖新增规则

- 后端：新增依赖 → 版本写进 `pom.xml` `<properties>` → 登记《技术架构与模块设计》§1 基准清单（版本号、用途、为什么不用现有库）→ 评审通过才可引入。
- 已有依赖能用就不新增；能用 JDK 标准库就不新增。
- 前端：运行时依赖从 3 个（vue/pinia/vue-router）起步，新增 UI 库/图表库/请求库需要 ADR（当前明确不引入 axios、不引入 UI 框架）。
- 禁止 SNAPSHOT 版本；禁止未锁版本范围的插件类依赖。

## 9. 存量偏差处理（祖父条款）

1. **只减不增**：附录里登记的偏差是"存量豁免"，新代码不得复制该写法。
2. **改动即合规**：一旦你改到某个文件/方法，就地把它在本文件的偏差修掉（机会式清理），并更新附录。
3. **豁免必须有退出条件**：每条豁免写「为什么现在不改」「什么条件下必须改」，不接受永久豁免。
4. **红线条款无豁免**：第 3 节十条红线没有祖父条款，发现即修。
