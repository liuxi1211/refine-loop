## 2. 单模块决策

**保持单 Maven 模块、按领域分包。** 理由：

- 个人项目，构建/部署链路越短越好（`mvn package` 一个 jar）；
- 包边界已经按"可拆分"设计（`common` 零业务依赖、领域包之间无循环），真要拆模块时是纯机械动作；
- 多模块的真实收益（独立版本、独立发布、编译隔离）在本项目规模下为负。

**拆分触发条件**（任一满足再考虑，不要提前优化）：出现第二个可独立部署的进程；单次 `mvn test` 超过 5 分钟；领域包数量 > 8 且每个都 > 50 个类。

### 3.1 包的命名与拆分阈值

| 规则 | 说明 |
|---|---|
| 顶层包 = 业务域（名词） | `tushare`、`ops`、`judgment`、`report`…；技术关切（`config`、`web`、`common`）例外 |
| 领域内部按**角色**拆子包，不按"层"堆文件 | `model`（领域值对象/枚举）/ `dto`（出入参）/ `service`（用例）/ `registry`（元数据） |
| 一个包超过 **15 个文件**，或同时容纳 **3 类以上角色** | 必须拆子包（`tushare/ingest` 就是按此规则拆的） |
| 不得为了"看起来整齐"建只有一个类的子包 | 少于 3 个类不单独建包，等它长大 |
| 包名全小写、单数、无下划线、无版本号 | `web/ops` ✓，`web/ops_center` ✗，`data/db2` ✗ |
| 每个顶层包必须有 `package-info.java` | 写「职责 / 允许依赖 / 不变量」，见 §10 |

## 4. 依赖方向（唯一权威矩阵）

**允许的依赖**（行依赖列）:

| from \ to | common | config | data | capability | ops | tushare | user | web |
|---|---|---|---|---|---|---|---|---|
| **common** | – | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| **config** | ✓ | – | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| **data** | ✓ | ✓¹ | – | ✗ | ✗ | ✗ | ✗ | ✗ |
| **capability** | ✓ | ✓³ | ✓ | – | ✗ | ✗ | ✗ | ✗ |
| **ops** | ✓ | ✓ | ✓ | ✗ | – | ✓ | ✗ | ✗ |
| **tushare** | ✓ | ✓ | ✓ | ✗ | ✗ | – | ✗ | ✗ |
| **user** | ✓ | ✓ | ✓ | ✗ | ✗ | ✗ | – | ✗ |
| **web** | ✓ | ✓ | ✗ | ✓ | ✓ | ✓² | ✓ | – |

1. `data → config` 只允许依赖**配置属性类**（如 `IngestProperties`、`AuthProperties`）；`config` 是装配根，不算领域层。
2. `web → tushare` 只允许依赖其**对外服务接口**（`IngestFacade`、`QualityCheckLogStore` 之类），不得依赖 `tushare.ingest.service.*Impl`。
3. `capability → config` 只允许依赖**配置属性类**（如 `LlmProperties`）；运行时类保持纯类，由 `config/*Config` 装配。

**硬性禁止**（`ArchitectureRulesTest` 校验）：

- `common` 依赖任何业务域（`ops`/`tushare`/`user`/`data`/`capability`/`web`）——`common` 是地基，反向依赖会造成"改一处崩全站"；
- `common` 内出现 `@RestController` / `@Controller`（web 适配器只能放 `web`）；
- `web` 依赖 `data.mapper` / `data.entity` / `data.provider` / `data.batch`；
- `web` 层出现 `@Transactional`；
- 领域包（`ops`/`tushare`/`user`）依赖 `web`；
- `user` 账号域依赖 `ops` / `tushare`（账号与运维、数据接入无耦合）；
- `capability` 依赖 `web`/`ops`/`tushare`/`user`/`pipeline`/`judgment`/`report`/`version`；
- `capability.spi` 依赖 `capability.runtime` / `capability.units` / `data`；
- `capability.runtime` 依赖 `capability.units`；
- `capability.units` 内的单元依赖另一个带 `@CapabilityUnit` 的单元（协作只通过 `FactBundle`）；
- `ChatClient` 直接注入/依赖出现在 `capability.runtime.llm` 之外；
- 任意两个包之间出现**循环依赖**；
- 生产代码使用 `org.springframework.jdbc.core.JdbcTemplate`；
- 生产代码使用 `System.out` / `System.err` / `printStackTrace()`；
- 生产代码使用 `java.util.Date` / `java.sql.Timestamp` / `Instant` 作为实体或 API 时间字段（统一 `LocalDateTime`）。

> 新增顶层包时，**必须**在矩阵里加一行并在 `ArchitectureRulesTest` 里登记，否则规则不生效。

## 5. 分层职责与禁止清单

| 层 | 包 | 只做 | 禁止 |
|---|---|---|---|
| 适配层 | `web` | HTTP 参数解析、入参校验、调服务、包 `Result`、错误翻译 | 直接访问 mapper/entity；拼业务文案；写库；`@Transactional` |
| 应用服务 | 领域 `service` | 用例编排、事务边界（写路径）、跨聚合协调 | 拼 SQL；返回实体给 web；依赖 `web`；静态可变状态 |
| 领域模型 | 领域 `model`/`dto` | 不可变值对象、枚举、状态语义 | 依赖 Spring 注解（除配置类）；持有可变共享状态 |
| 数据访问 | `data` | SQL、映射、批处理、类型处理 | 业务判断；事务策略；日志打印大对象 |
| 基础设施 | `common` | 与业务无关的通用能力 | 引用业务类型；`@RestController`；业务常量 |

**判断口诀**：`web` 只认识"请求和响应"；`service` 只认识"用例和数据"；`data` 只认识"表和列"；`common` 谁也不认识。

## 7. 测试目录规范

**测试包必须与主代码包同构**（`web/ops` 的测试放 `src/test/java/.../web/ops/`），这样"这个类有没有测试"不需要搜索。

| 测试类型 | 位置 | 命名 |
|---|---|---|
| 单元/切片（占多数） | 与主代码同构的包 | `<被测类>Test`（如 `IngestLogServiceTest`） |
| 跨模块集成 | `it/`（专门目录） | `<场景>IntegrationTest` |
| schema/DDL 校验 | `schema/` | `<关注点>Test`（`SchemaSqliteTest`、`SchemaConventionTest`） |
| 架构守卫 | `architecture/` | `ArchitectureRulesTest` |
| 测试夹具 | `support/` | 无 `Test` 后缀（`SchemaTestSupport`、`MutableClock`） |

例外：`com.example.dictfixture.*` 是字典扫描的**故意越界夹具**（必须在包外才能验证"只扫描本项目包"），已在 `DictServiceTest` 注释说明，属登记例外。

## 8. 依赖新增

见总纲 §8。结构视角的补充：

- 新依赖不得改变分层（例如引入一个"万能 DAO 库"绕过 `data` 层 → 拒绝）；
- 工具库优先选"零传递依赖/体积小/持续维护"的（当前：Guava、fastjson2、Hutool 未使用则删）；
- 前端禁止引入 UI 框架/请求库（`axios`）/状态库替代品；现有 3 个运行时依赖是上限基准。
